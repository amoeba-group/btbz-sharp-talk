# FIX-260917 — 커스텀 위젯 모서리 설정이 패널 껍데기 하나에만 적용되던 결함

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-17 |
| 보고 | 김익용 (`ambshop-dev.myshopify.com` 실조사) — REQ-260917 |
| 계획 | PLN-260917 · 검증 TCR-260917 |
| 성격 | 프런트엔드(위젯·콘솔·공유 types) — API/DB/백엔드·스키마 무변경 |

## 1. 증상

테넌트가 모서리를 `작게/보통/크게`로 바꿔도 위젯에 체감 변화가 없었습니다. 데스크톱
패널의 바깥 모서리만 몇 픽셀 움직였고, 그것도 640px 이상에서만.

## 2. 근본 원인

라운딩 토큰이 **테마 주입 레이어에만 도입되고 컴포넌트 레이어로 전파되지 않았습니다.**
`--ivy-radius`를 소비하는 CSS 규칙은 전체 스타일시트에서 **단 하나**(`.ivy-panel-desktop`)
였고, 나머지 56개 호출부는 Tailwind 고정 유틸(`rounded-lg` 등)을 쓰고 있었습니다.

저장·전달·테넌트 해석·캐시는 전부 정상이었습니다 — 같은 레이어를 쓰는 폰트·패널 크기
토큰은 잘 동작했습니다. 즉 **배관 누락**이지 파이프 고장이 아니었습니다.

## 3. 수정

**설계를 뒤집었습니다**: 원시값 하나를 노출하고 컴포넌트가 손으로 참여하기를 기대하는
대신, 테마 레이어가 **5단 파생 스케일**을 발행하고 컴포넌트는 **이름**(`rounded-st-*`)만
소비합니다. 픽셀값은 더 이상 컴포넌트에 등장하지 않습니다.

- `radiusVars()`(공유 패키지) — `RADIUS_SCALE` 0.33/0.5/0.67/1/1.33, `[2,28]` clamp.
  보정 기준: **`보통`에서 파생값이 기존 하드코딩 값과 정확히 일치**(4/6/8/12/16px) →
  기본 테넌트 무회귀.
- Tailwind `rounded-st-{xs,sm,md,lg,xl}` 등록(폴백 = 구 고정값).
- 패널 컴포넌트 **57개소** 이행. 핀/원형 25·모바일 사각 1·말풍선 꼬리 1은 의미 있는
  형태라 제외. 개발용 모의 상점(`components/storefront/`)도 제외 — 머천트 사이트를
  흉내 내는 화면이라 우리 테마를 따르면 안 됨.
- 콘솔 편집기 미리보기가 **같은 `radiusVars()`** 를 주입 → 상수 중복 없이 정합.

### 3-1. 스테이징 실측에서 추가로 드러난 누락

배포 후 실위젯의 계산값을 순회하다 스케일 밖 값(4px)을 발견했습니다 — **접두어 없는
`rounded`**(Tailwind 4px)가 첨부 칩·썸네일·경고 배너 등 **10개소**에 남아 있었고,
원 보고서의 집계표에도·1차 이행 정규식에도·가드에도 빠져 있었습니다. 원 버그와 정확히
같은 실패 방식이 수정 안에서 재현된 셈입니다.

4px는 기존 최하단(`sm`=6px)보다 작아 `sm`으로 올리면 기본 설정에서 눈에 보이는 변화가
생기므로(NFR-001 위반), **`xs` 단(0.33 → 보통에서 정확히 4px)** 을 신설해 이행하고
가드 정규식도 접두어 없는 형태까지 잡도록 보강했습니다.

### 3-2. 함께 잡은 숨은 갭 (원 보고서에 없던 것)

`apps/widget/src/lib/theme.ts`의 `THEMED_PROPERTIES`는 "테마 해제 시 지울 속성" 목록
입니다. 파생 변수 5개를 여기에 추가하지 않았다면, 테넌트가 **커스텀 디자인을 해제하거나
다른 디자인으로 바꿀 때 낡은 모서리가 그대로 남았을** 것입니다 — 이번 버그의 정반대
증상이고, 역시 아무 에러도 내지 않는 종류입니다.

## 4. 예방 패턴

**① 정적 검사로 "전부 고쳤다"를 선언하지 않는다 — 배포본의 값 분포를 본다.**
1차 이행은 grep 기준으로 완결처럼 보였지만, 실위젯 계산값을 순회하자 스케일 밖 값이
남아 있었습니다(§3-1). 토큰 이행은 **"패턴을 몇 개 바꿨나"가 아니라 "렌더된 값이 전부
스케일 안에 있나"** 로 판정해야 합니다.

**② 디자인 토큰은 "발행처"가 아니라 "소비처"로 완결을 판정한다.**
`--ivy-radius`는 만들어졌고, 전달됐고, 테스트도 통과했지만 **아무도 쓰지 않았습니다.**
새 토큰을 추가할 때는 소비처를 grep으로 세고, 세어본 수가 기대와 다르면 배관이 덜 된
것입니다. ([[computed-token-nobody-consumes]]와 동일 계열 — 그때는 `text-white` 14곳이
토큰을 무시했습니다.)

**③ 조용히 실패하는 규칙은 CI로 고정한다.**
고정 라운딩은 에러를 내지 않고 그냥 설정을 무시합니다. 그래서 `npm run radius:check`
(CI 게이트)가 패널 컴포넌트의 고정 라운딩(접두어 없는 `rounded` 포함)을 차단하고 대체
토큰을 지목합니다. 수정보다 **수정이 썩지 않게 하는 장치**가 본질입니다.

**④ "지우는 목록"이 있으면 "만드는 목록"과 짝을 맞춘다.**
변수를 추가하는 코드와 제거하는 코드가 다른 패키지에 있으면 반드시 벌어집니다. 특정
변수 5개를 검사하는 대신 **빌더가 쓰는 모든 `--ivy-*`가 해제 목록에 있는지**를 보는
일반 계약 테스트를 뒀습니다 — 다음에 누가 무슨 변수를 추가하든 작동합니다.

## 5. 검증

TCR-260917: 로컬 17/17 통과. 브라우저 계산값 실측에서 **보통 열이 기본 열과 완전히
동일**(무회귀 실증 — xs 4px 포함), 작게/크게는 POL-001 표와 일치, 런처는 전 설정 9999px, 모바일 0px.
가드·계약 테스트는 각각 역검증(결함 주입 시 실패)까지 확인.

## 5-1. 배포 중 겪은 운영 이슈 (라운딩과 무관, 기록용)

xs 보강분 배포에서 `deploy-staging.sh`가 **Docker 컨테이너 이름 충돌로 실패했는데도
exit 0을 반환**했습니다. 처음엔 "배포됐다"로 보였지만 번들 해시가 그대로여서 실패를
알아챘고, 재시도 과정에서 충돌이 연쇄되어 `web`·`widget` 컨테이너가 제거된 뒤 재생성되지
못해 **스테이징이 일시적으로 502**였습니다.

- 원인: 이전 배포가 남긴 **`created` 상태 고아 컨테이너**(`<old-id>_<name>` 형태의 compose
  rename 잔재)가 이름을 점유. 기동 이력이 전무(`StartedAt=0001-01-01`)한 잔재였습니다.
- 복구: 고아 4개 제거 후 재배포 → 전 컨테이너 재생성, 공개 URL 3종 200, API 부팅 정상.
- **교훈**: 저장소의 "배포는 종료 코드가 아니라 내용으로 판정한다"가 정확히 이 상황을
  막아줬습니다. 다만 **스크립트가 실패를 종료 코드로 전파하지 않는 것 자체는 결함**이라
  별도 개선 권장(`docker compose up` 실패 시 non-zero 반환 + 고아 컨테이너 사전 정리).
