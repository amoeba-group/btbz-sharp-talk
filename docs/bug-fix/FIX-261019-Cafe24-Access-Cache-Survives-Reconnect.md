# FIX-261019 Cafe24 재연결 후에도 구 액세스 토큰이 최대 2시간 사용되던 결함 (토큰 캐시가 자격증명을 따라가지 않음)

- 작성일: 2026-10-19 · 발견: PLN-261019-Cafe24 배포 직후 스테이징 실측(사용자가 amoebaorder를 16:52 UTC에 두 번 재연결했는데 연결 테스트가 계속 403 insufficient_scope)
- 범위: API `Cafe24TokenService` 1파일 + 스펙 · 스키마 변경 없음

## 증상
콘솔 "Cafe24 재연결"로 새 동의(OAuth callback → `upsertCredential`로 refresh 토큰 교체, 감사 `tenant.credential_rotated` 16:52:01·16:52:21)를 마친 직후 "연결 테스트"가 여전히 `/products`·`/orders` 403 insufficient_scope. 로그에 refresh 호출이 없음(테스트 285ms = 읽기 2회뿐).

## 근본 원인
`Cafe24TokenService.accessCache`(테넌트별 메모리, TTL≈2h)가 **자격증명 행과 무관하게 테넌트 id만으로** 조회된다. `getConnection()`은 캐시가 살아 있으면 저장된 자격증명을 읽기만 하고 refresh를 건너뛰므로, 재연결로 행이 새 refresh 토큰으로 바뀌어도 **이전 grant로 발급된 액세스 토큰을 만료(≤2h)까지 계속 사용**한다. 권한이 줄어든 몰을 재인가해도 동기화·테스트가 그대로 403을 내는 이유. 16:50:36 사용자의 주문 동기화가 구 자격증명으로 캐시를 채운 뒤, 16:52 재연결·테스트가 그 토큰을 썼다.

## 수정
- 캐시 항목에 `credKey = sha256(secret_enc)`를 함께 저장하고, `getConnection()`은 **현재 행의 키와 같을 때만** 캐시를 쓴다. 다르면(재연결·수동 저장) refresh.
- 토큰 서비스 자신이 회전 저장한 경우는 저장 후의 `secret_enc`로 키를 만들므로 자기 캐시를 무효화하지 않는다(불필요한 refresh 없음).
- 스펙 3건: 불변이면 재사용(fetch 1회) · 행 교체 후 재발급(fetch 2회) · 자체 회전은 캐시 유지.

## 영향
- 재연결 직후 첫 호출이 refresh 1회 추가(정상). 다른 경로 무변경. 재시작 시 캐시는 원래 비워지므로 배포 자체가 즉시 효과.
- 롤백: 코드 되돌림.

## 예방 패턴
- **메모리 캐시의 키에는 "무엇으로부터 파생됐는가"를 넣는다.** 테넌트 id만으로 캐시한 파생 비밀(액세스 토큰)은 원본(refresh 토큰)이 바뀌어도 살아남는다. 원본의 지문(해시·updated_at)을 캐시 항목에 넣고 조회 때 대조.
- 재인가·재설정 같은 "원본 교체" 경로를 추가할 때는 그 원본에서 파생된 캐시를 전수 grep(`Cache.get(`)해 무효화 조건을 확인.
