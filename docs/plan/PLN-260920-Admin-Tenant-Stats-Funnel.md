## 1. 설계 요지

### 1.1 하나의 집계, 두 개의 화면

같은 7단계를 테넌트 콘솔(자기 것)과 어드민(전 테넌트 × 행)에서 봅니다. 계산이 두 벌이
되면 반드시 갈라지므로 **`journeyStages(tenantId, window)` 하나**를 만들고, 어드민은
그것을 테넌트별로 돌리는 대신 **단일 GROUP BY 쿼리**로 같은 정의를 재현합니다
(REQ §3.4 — N+1 금지). 정의가 두 곳에 사는 것을 막기 위해 **SQL 표현식 상수를 공유**하고,
두 경로가 같은 수를 내는지 **대조 테스트**로 고정합니다.

### 1.2 깔때기와 분해를 시각적으로 구분 (REQ §3.1)

| 구간 | 성격 | 분모 |
|---|---|---|
| 노출 → 접속 → 대화 | **진짜 깔때기**(각 단계가 앞의 부분집합) | 앞 단계 |
| 에이전트 · 상담원 이관 · 평가 · 종료 | **대화의 속성 분해**(서로 배타 아님) | 대화 |

화면에서 앞 3칸은 `→`로 잇고, 뒤 4칸은 "대화 중 n%"로 나란히 둡니다. 같은 모양으로
그리면 "종료 95%인데 평가 3%"가 결함처럼 읽힙니다.

## 3. 단계

### S1 — 공유 집계 (`journeyStages`)
- `analytics-breakdown.service.ts`에 `journeyStages(tenantId, window)` 추가.
  반환: `{ impressions, opens, openedSessions, conversations, aiHandled, escalated, rated, ended }`.
- 1·2단계는 PLN-260920의 세션 집계를 재사용(대화로 열람을 유도하는 규칙 포함).
- 4~7은 `conversations` 한 번 조회 + `messages`의 AI 발신 집계로 계산.

### S2 — 어드민 크로스테넌트 라우트
- `GET /admin/analytics/tenants?from&to` — **`@AdminOnly()`**.
- **단일 GROUP BY**로 테넌트별 행 생성(N+1 금지). `tenantOf` 게이트는 건드리지 않음 —
  기존 테넌트 라우트는 계속 시스템 관리자를 막습니다(REQ §1.2).
- 반환에 대화 내용·고객 식별자 없음(집계 수치 + 테넌트 이름/슬러그만).
- 정의 일치 대조 테스트: 같은 테넌트에 대해 `journeyStages`와 GROUP BY 결과가 동일.

### S3 — 어드민 화면
- `AdminOverviewPage`의 빈 KPI 3장을 실값으로 교체(활성 테넌트·노출·대화).
- 그 아래 테넌트별 표(§2.1). 기간 필터는 테넌트 콘솔과 동일 컴포넌트 관례.
- i18n 6로케일(`overview` 네임스페이스).

### S4 — 테넌트 콘솔 여정 탭
- `SECTIONS` 맨 앞에 `journey` 추가 → `['journey','questions','access',…]`.
- `JourneySection.tsx` 신설(§2.2). 각 줄에서 기존 탭으로 이동.
- i18n 6로케일(`statistics`).

### S5 — 검증·배포
- 단위: 깔때기 단조성(노출≥접속≥대화), 분해 4종의 분모=대화, 수집 이전 구간에서
  1·2단계가 0이어도 3~7이 정상 표시, 어드민/테넌트 경로 정의 일치.
- 스테이징 실데이터로 두 화면 확인 → TCR/RPT.
- **스키마 변경 없음** → 마이그레이션 불요.

## 4. 측면 영향

- 기존 6개 렌즈 탭의 쿼리·정의는 **무변경**. 탭 추가와 순서만 바뀝니다.
- 어드민 라우트는 신규이므로 기존 권한 경계에 영향 없음. `tenantOf`의 크로스테넌트
  차단은 **그대로 유지**됩니다(그 게이트를 여는 게 아니라 옆에 다른 문을 냅니다).
- 노출·접속 미수집 구간에서 1·2단계가 0으로 보이는 것은 정상 — 화면이 수집 시작일을
  밝혀 "데이터가 없는 것"과 "0인 것"을 구분합니다.
