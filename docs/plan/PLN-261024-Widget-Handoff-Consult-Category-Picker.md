# PLN-261024 — 상담카테고리: 명칭 · 노출 설정 · 위젯 고객 선택 · 규칙 기반 그룹 연결

- REQ: `docs/analysis/REQ-261024-Widget-Handoff-Consult-Category-Picker.md` (§6 추가 요구 포함)
- 상태: **승인됨** (2026-10-24, D1~D8 권장안)
- 개정: 2026-10-24 추가 요구 반영. 상담카테고리는 고객 선택값과만 맞추고, 지역은 고객 정보 조건으로 옮기며, go2joy 5개는 삭제한다.

## 1. 개념 정리

| | 상담카테고리 | 지역(권역) |
|---|---|---|
| 뜻 | 고객이 고르는 상담 주제(예약, 결제, 객실 등록 …) | 고객(호텔)의 위치: 북부·중북부·중부·중남부·남부 |
| 목록 | 테넌트가 관리(`routing_categories`) | 고정 5개(Go2Joy 표, `REGION_CODES`) |
| 값의 출처 | 위젯에서 고객이 선택 → `conversations.consult_category` | 호스트 앱이 서명한 `identity_attributes.region`, 기업 `companies.region` |
| 배정 규칙에서 | **상담카테고리** 줄(칩) | **고객 정보** 조건 `권역`(신규), `지역(성)`(기존) |

**연결 규칙**
1. 규칙을 위에서부터 확인한다.
2. 상담카테고리(고객 선택) AND 업무 AND 고객 정보(권역·성 등)가 **모두 맞는 첫 규칙**을 고른다.
3. 그 규칙의 **상담원 그룹(팀 × 라벨)**과 개인 지정 중 접속 중인 상담원에게 연결한다. 연결 방식은 규칙에 정한 "가장 한가한 1명" 또는 "전원 알림"이다.
4. 맞는 규칙이 없으면 위의 담당 상담원에게 간다(지금과 같음).

예:

| # | 규칙 | 상담카테고리 | 고객 정보 | 그룹 |
|---|---|---|---|---|
| 1 | 결제 · 북부 | 결제 | 권역 = 북부, 중북부 | 팀 하노이 CS × 라벨 회계 |
| 2 | 결제 · 남부 | 결제 | 권역 = 중남부, 남부 | 팀 호찌민 CS × 라벨 회계 |
| 3 | 예약 | 예약 | (전체) | 라벨 상담 |
| 4 | 기본 | (전체) | (전체) | 라벨 상담 |

## 2. 결정 사항 (권장안 ★)

| # | 결정 | 권장 |
|---|---|---|
| D1 | AI 인계(B 경로) 선택 시점 | ★ 바로 호출하고, 고객이 고르면 재라우팅한다. 호출을 늦추지 않는다. |
| D2 | 재라우팅 조건 | ★ 아직 아무도 수락하지 않은 대기 대화에서 첫 선택 1회만 |
| D3 | 상담카테고리 조건과 맞추는 값 | ★ **고객이 고른 값만** 본다. 서명 region은 상담카테고리와 비교하지 않는다. 고르지 않으면(건너뛰기) 상담카테고리 조건이 있는 규칙은 건너뛰고, 조건 없는 규칙으로 간다. |
| D4 | 직전 상담원 우선 | ★ 고객이 고르면 건너뛰고 규칙을 따른다. 고르지 않으면 지금처럼 직전 상담원이 우선이다. |
| D5 | 고객에게 보일 이름 | ★ 기본 이름 + 언어별 이름(선택 입력) |
| D6 | 노출 기본값 | ★ 새로 만들 때 노출함(추가 줄 체크로 끌 수 있음). 기존 행은 D8로 삭제되므로 남는 것이 없다. |
| D7 | [건너뛰기] | ★ 항상 표시 |
| D8 | go2joy 지역 5개 정리 | ★ 데이터 SQL로 한다. (1) 팀·라벨 담당 범위에서 그 5개 코드를 뺀다. (2) 규칙 상담카테고리 조건에 그 코드가 있으면 고객 정보 `권역` 조건으로 옮긴다(스테이징 0건). (3) 기본 투입 행(name NULL)만 삭제한다. 프로덕션은 0행이라 할 일이 없다. |

**"상담카테고리 담당자에게 배정"(팀·라벨 담당 범위) 처리**: 그룹 배정과 별도인 기존 선택 기능이다.
- 담당 범위는 **상담카테고리 + 성·시**가 된다(권역 칩은 상담카테고리 칩이 됨).
- 고객이 고른 상담카테고리 또는 고객의 성·시를 담당하는 사람을 고른다.
- 주된 연결 방식은 위의 규칙 그룹(팀 × 라벨)이다. 이 기능은 그대로 두는 보조 수단이다.

## 4. 단계별 작업

### S1. 스키마 + 데이터 (SQL 먼저 적용)
**`sql/261024-consult-category.sql`**
- `routing_categories`
  - `ADD visible TINYINT(1) NOT NULL DEFAULT 0`
  - `ADD names JSON NULL`
- `conversations`
  - `ADD consult_category VARCHAR(64) NULL`
  - `ADD consult_category_at DATETIME(6) NULL`
- **D8 정리**
  - `units.regions`와 `job_labels.regions`에서 5개 코드를 뺀다(JSON_TABLE로 걸러 다시 집계, 비면 NULL).
  - 규칙 JSON의 regions에 5개 코드가 남은 테넌트가 있는지 확인하는 SELECT를 넣는다. 있으면 콘솔에서 옮긴 뒤 진행한다(스테이징·프로덕션 모두 0건 확인).
  - `DELETE FROM routing_categories WHERE code IN (5개) AND name IS NULL`
- 이 파일 이후로 #727의 기본 투입 SQL은 다시 실행하지 않는다. 프로덕션에 go2joy를 이관할 때도 5개를 넣지 않는다.
- 엔티티에 nullable `type`을 명시하고 `migrations:manifest`를 갱신한다.

### S2. API
- **라우팅**
  - `RoutingContext`에 `consultCategory?`를 추가한다.
  - 규칙 상담카테고리 조건(`rule.regions`, 저장 키는 유지)은 `consultCategory`와 비교한다(D3). 서명 region 비교는 없앤다.
  - 고객 정보 조건 카탈로그(`packages/types` routing-condition)에 `region`(enum, 고정 5개, `canonicalRegion` 비교, source identity)을 추가한다.
  - 보조 배정(`assigneeByRegion`): 담당 범위 regions는 `consultCategory`, provinces는 성·시와 비교한다.
  - 직전 상담원 우선은 `consultCategory`가 있으면 건너뛴다(D4).
  - 로그에 `category=…`를 남긴다.
- **상담카테고리 API**
  - create/update에 `visible`과 `names`를 추가한다(새로 만들 때 기본 visible=true).
  - `visibleFor(tenantId, language)`, `isVisible(tenantId, code)`를 추가한다.
  - 사용처 집계와 삭제 거부에서 기업을 뺀다(G15).
- **기업**: `ListCompaniesQuery.region` 검증을 `@IsIn(REGION_CODES)`로 되돌린다.
- **위젯**
  - ensure 응답에 `consultCategories: [{code,label}]`(세션 언어로 해석, 노출함만, 순서대로)를 넣는다.
  - `POST /chat/escalate`에 `category_code?`를 받는다. 노출함이면 저장하고 시스템 줄을 남긴 뒤 그 값으로 라우팅한다.
  - `POST /chat/consult-category`: 소유·노출 검사, 저장, 시스템 줄. 미수락 대기에서 첫 선택이면 재라우팅하고 ESCALATION을 다시 발행한다(`reason: category_selected`).
  - `sendMessage` 응답에 `handedOff`를 추가한다.
  - 숨김·없는 코드는 E5109로 거부하고 `logger.warn`(escalate는 무시하고 기본 라우팅).
- **콘솔 상세**: 대화 응답에 `consultCategory {code,label}`를 넣는다.
- **알림**: 에스컬레이션 이벤트·알림 메일 본문에 상담카테고리를 넣는다.

### S3. 위젯
- `ConsultCategoryCard.tsx`: 칩 + [건너뛰기]. 테마 토큰과 반경 토큰을 쓴다.
- `ChatTab`
  - A 경로 4곳을 `requestAgent()`로 모은다. 노출 목록이 있으면 카드(before), 없으면 바로 escalate.
  - B 경로는 `handedOff`이고 목록이 있으면 카드(after)를 띄운다. 한 대화에 한 번만.
- 위젯 i18n 6개 언어.

### S4. 콘솔
- 명칭 "카테고리"를 "상담카테고리"로 바꾼다(6개 언어). 규칙 안내 문구를 "…첫 규칙의 상담원 그룹에 연결"로 바꾼다.
- 관리 모달: 노출 토글, 언어별 이름, 추가 줄 노출 체크.
- 규칙 칩에 👁(노출) 표시를 붙인다. 고객 정보 조건에 `권역`(칩 5개)을 추가한다.
- 팀·라벨 담당 범위 문구를 "상담카테고리 + 성·시"로 바꾼다.
- 기업 지역 필터를 고정 권역으로 되돌린다.
- 라이브챗 헤더에 `상담: X` 배지를 단다.

### S5. 문서·배포
- TCR과 RPT를 작성한다. SQL 선적용 후 스테이징 → 프로덕션 순으로 배포한다. PR에 `## Migration`.

## 6. 테스트 계획
- **단위**
  - 라우터: 상담카테고리 = 고객 선택만, 권역 조건, 선택 + 권역 AND, 건너뛰기 시 조건 없는 규칙, 직전 상담원 건너뛰기, 보조 배정
  - 상담카테고리: 노출·언어별 이름 저장과 해석, 기업 사용처 제외
  - escalate와 consult-category: 노출 검사, 소유, 첫 선택만 재라우팅, 배정된 대화는 기록만
  - ensure: 빈 배열과 언어별 해석
- **통합(로컬)**
  - 3-1의 예 규칙 4개를 만들고 권역이 다른 세션으로 결제·예약·건너뛰기를 고른다. 연결 대상 그룹(로그 rule·targets)을 확인한다.
  - B 경로 재호출 1회
  - D8 SQL을 로컬 사본에서 실행해 전후를 비교한다.
- **화면**: 규칙 편집(권역 조건·👁), 관리 모달, 위젯 카드(ko·vi·en), 콘솔 배지, 기업 필터
