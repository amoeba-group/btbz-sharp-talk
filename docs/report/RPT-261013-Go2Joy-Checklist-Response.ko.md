## 1. 경영진 요약

### 1.1 결론

Stage 1에서 Amoeba가 맡은 부분은 **소스 코드 수준에서 거의 완전히 구축되었고 Amoeba의 로컬 환경에서 검증되었습니다.** 서명된 신원 브리지(SSO), 관리자·프런트 역할별 콘텐츠 접근 제어, 비로그인 방문자 게이트, 호텔 단위 파일럿 플래그, 팀·지역별 CS / Sales Admin 라우팅, 파트너 데이터 조회 모듈, 파일럿 지표, PDPL 대응(초안), Go2Joy 자체 인프라용 배포 패키지, 베트남어 운영 매뉴얼이 포함됩니다.

**Go2Joy의 입력 없이는 완료할 수 없는 것**을 일정 영향이 큰 순서로 적습니다.

1. 파트너 API 명세와 키(R8, R9) — Gate 3 "실데이터로 응답"을 좌우합니다.
2. Hotel Admin·Super Admin 계정(R1, R2) — 역할별 메뉴 맵과 격리 UAT를 좌우합니다.
3. Go2Joy 서버에서 identify 서명을 생성하고, 호텔 전환·로그아웃 시 다시 호출하는 것(R7).
4. PDPL 고지문의 법적 책임 주체(R16), 파일럿 호텔 목록(R14), 호스팅 위치(R6).

### 1.4 분명히 알아 두실 다섯 가지

1. 방문자 게이트의 임계값은 **실제 임베딩(Voyage + Qdrant)으로 측정하지 않았습니다.**
2. 파트너 데이터 조회는 실제 API가 없어 지금까지 **샘플 데이터와 가짜 서버**로만 동작했습니다.
3. Go2Joy 인프라용 설치 패키지는 **한 번도 실제로 빌드하거나 실행하지 않았습니다.**
4. PDPL 문구와 번역은 변호사·원어민의 검토를 받지 않았습니다.
5. 실제 모델 기준 성능과 비즈니스 지표(재예약)는 **아직 측정할 수 없습니다.**

## 2. 문서 읽는 법

### 2.1 상태 기호

| 기호 | 의미 |
|---|---|
| ✅ | 코드로 구현되었고 Amoeba 로컬 환경에서 검증됨 (자동 테스트, 실제 API 부팅, HTTP 스모크, 브라우저 검증 — 검증 수준은 각 항목에 명시). **Go2Joy의 실제 시스템에서는 아직 실행하지 않음.** |
| 🟡 | 일부만 구축되었거나, Go2Joy의 입력이 없어 Amoeba가 직접 작성한 계약에 맞춰 구축됨 |
| 🔴 | 입력이 없어 아직 불가능함 |
| ⬜ | Go2Joy가 할 일 |

**"완료"는 "스테이징/프로덕션에서 실행 중"이라는 뜻이 아닙니다.** 모든 코드는 PR을 기다리는 하나의 브랜치에 있으며, 배포 전에 신규 SQL 파일 19개를 먼저 적용해야 합니다(스테이징에는 `261001-guest-login-gate.sql`이 10/07에 이미 적용되어 18개가 남음. 스테이징은 `DB_SYNCHRONIZE=false`로 운영).

### 2.2 각 R 항목의 구성

R1–R16 각 요청은 다섯 부분으로 고정하여 회신합니다. **판단**(왜 중요한가), **상태**(무엇을 했고 어떻게 검증했는가), **산출물**(구체적인 파일·화면·API), **Go2Joy에 필요한 것**(할 일과 기한), **장기적 가치**.

## 5. Go2Joy 요청 사항(R1–R16)에 대한 상세 회신

### A. 계정과 접근 (R1–R3)

#### R1 — Hotel Admin 테스트 계정
*관리자(다중 호텔) 1개 + 프런트(단일 호텔) 1개, 테스트 호텔·객실·예약 데이터 포함. 기한 10/13.*

- **판단.** Phase 1에서 가장 중요한 입력입니다. 두 역할은 identify v2 서명의 `manager`, `receptionist`에 그대로 대응하며 콘텐츠 경계(정산, 은행 계좌 변경, 직원 권한은 관리자 전용)를 결정합니다. 실제 계정이 없으면 Amoeba는 공개 문서와 시뮬레이션으로 권한 범위를 추정할 수밖에 없습니다.
- **상태.** 🔴 계정 미수령(Amoeba가 아는 범위). 막히지 않기 위해 한 일: ✅ 서명과 지식 접근 등급에 세 역할(`manager`, `receptionist`, Go2Joy 직원용 `internal`)을 모델링, ✅ 다중 호텔 시뮬레이션 데이터로 격리 테스트 작성, 🟡 기본 지식베이스는 공개 Hotel Admin 화면을 바탕으로 작성했으며 실제 계정과 대조하지 않음.
- **산출물.** 역할·등급 열거형(`packages/types/src/common/enum.types.ts`, `audience.ts`), 테스트 `embed.service.rebind.spec.ts`, `embed.service.v2.spec.ts`.
- **Go2Joy에 필요한 것.** 스테이징 계정 2개, 관리자 계정용 호텔 최소 2곳("호텔 전환" 검증용), 각 호텔의 시·도(지역 라우팅 검증용).
- **장기적 가치.** 역할에 맞는 접근 제어는 호텔 사장이 어시스턴트를 **신뢰**하게 만듭니다. 프런트 직원은 관리자의 금전 내용을 보지 못하고, 관리자는 일반적인 답변을 받지 않습니다. 이 신뢰가 장기 사용과 일회성 시험을 가릅니다.

#### R2 — Super Admin 계정 또는 시연
*조회 전용/제한 권한. 불가하면 화면 공유 시연 + 메뉴 목록. 기한 10/13.*

- **판단.** "Go2Joy 직원이 호텔을 지원하는 업무" 중 어시스턴트가 대신할 수 있는 영역(자동 응답 / 조회 / 처리 보조 / 사람 이관)을 찾는 입력입니다. 계정 발급이 하루 이상 늦어지면 시연 방식을 권장합니다(10장).
- **상태.** 🔴 미수령. ✅ 분류 결과를 받을 자리는 이미 구축: 지식 접근 등급, CS/SA 팀, 팀·지역별 대기열.
- **산출물.** Go2Joy 콘솔: Users & Labels, Agent handoff, Live chat 대기열 (매뉴얼 `apps/web/public/manual/go2joy-ops.vi.md` 1장, 3장, 5–6장, 영문 요약판 `go2joy-ops.en.md` 참조).
- **Go2Joy에 필요한 것.** 조회 전용 계정 또는 시연 일정.
- **장기적 가치.** 직원이 수작업하던 업무를 어시스턴트가 덜어 줄 때마다 규모가 커질수록 CS 비용이 줄어듭니다. 비용 규율과 적은 인력이라는 Go2Joy의 상황에 맞는 방향입니다.

#### R3 — 스테이징 접속 정보
*Hotel Admin 스테이징 URL, 제한 시 IP 화이트리스트 또는 VPN. 기한 10/13.*

- **판단.** 실제 로그인 페이지에서 Go2Joy의 실제 CSP 아래 위젯을 검증하기 위한 조건입니다. 없으면 모의 페이지에서만 검증할 수 있습니다.
- **상태.** 🔴 미수령. ✅ Amoeba는 모의 호스트 페이지(로더, 숨김/표시, 신원 만료 이벤트)로 실제 브라우저 검증을 마쳤습니다.
- **산출물.** 2개 국어 CSP/CORS 가이드(R5).
- **Go2Joy에 필요한 것.** URL과 접속 방법.
- **장기적 가치.** CSP/CORS 충돌을 일찍 찾으면 파일럿 당일 "위젯이 안 보인다"는 사고를 막을 수 있습니다. 첫날 신뢰를 무너뜨리는 유형의 장애입니다.

### B. 스테이징 선적용 (R4–R6)

#### R4 — 스테이징 로그인 페이지에 embed.js 삽입
*한 줄, 프런트엔드 담당자 지정. 기한 10/14.*

- **판단.** 삽입 자체는 간단합니다. 주의할 점은 **로그인 전 동작**(로그인 페이지는 모두가 "방문자"인 곳)과 로그인 후 위젯이 상태를 올바로 전환하는 것입니다.
- **상태.** ✅ 로더 준비 완료: 신원 확인 경로와 iframe 제목을 설정할 수 있고, 되돌릴 수 있는 숨김/표시(예: 파일럿 밖 호텔에서는 숨겼다가 호텔을 바꾸면 다시 표시), 신원 만료 시 호스트에 이벤트 전달. 🟡 Go2Joy의 실제 로그인 페이지에서는 아직 검증하지 않음.
- **산출물.** `apps/widget/public/embed.js`, SDK 가이드의 이벤트·숨김/표시 절, 위젯 테스트 155건 통과.
- **Go2Joy에 필요한 것.** 코드 한 줄 삽입, 담당자 지정.
- **장기적 가치.** 코드 한 줄에 호스트 UI 변경이 없어 통합 비용이 낮고, 이후 다른 Hotel Admin 페이지로 넓힐 때 새 프로젝트가 필요 없습니다.

#### R5 — CSP · CORS 허용
*위젯·API 도메인을 `script-src`, `frame-src`, `connect-src`와 CORS에 등록. 기한 10/14.*

- **판단.** "위젯이 로드되지 않는" 위험의 대부분이 여기서 나옵니다. 올바른 CSP는 필수입니다.
- **상태.** ✅ Amoeba가 가이드의 모든 서술을 코드(로더, iframe, 폰트, GA4)와 대조해 확인하고 지시어별 가이드를 작성했습니다. `script-src`(위젯 출처. 콘솔의 삽입 코드는 인라인이므로 nonce 또는 별도 파일 필요), `frame-src`/`child-src`, `connect-src`(위젯 출처와 `'self'`), 호스트에는 `img/style/font` 허용이 필요 없음. CORS는 정확한 출처 목록을 사용(와일드카드 불가). ✅ 위젯 nginx에 환경 변수로 제어하는 `frame-ancestors` 추가, ✅ Pretendard 폰트를 로컬에 포함하고 `WIDGET_FONT_CSS_URL`로 활성화(Go2Joy 프로필에 설정됨. 시스템 기본값은 여전히 jsDelivr). 이미지를 빌드하지 않아 `nginx -t`는 실행하지 못했습니다.
- **산출물.** `docs/guide/GUIDE-261013-Go2Joy-HotelAdmin-CSP-CORS.md`(vi/en), 변수 `CORS_ORIGINS`(`docs/guide/ENV-Config-Guide.md`, `apps/api/src/main.ts`, env 템플릿), `WIDGET_FRAME_ANCESTORS`, `WIDGET_FONT_CSS_URL`(`CONFIG.md`와 env 템플릿).
- **Go2Joy에 필요한 것.** 가이드에 따라 설정 적용, Hotel Admin 출처 목록 제공.
- **장기적 가치.** "누가 임베드할 수 있는가"를 제한하면 Go2Joy의 브랜드와 데이터가 보호됩니다. 한 장짜리 가이드는 프런트엔드 팀이 처음부터 올바르게 적용하도록 돕습니다.

#### R6 — SharpTalk 스테이징 위치
*Go2Joy 인프라 내, 또는 더미 데이터로 Amoeba 스테이징 사용 동의. 기한 10/14.*

- **판단.** Amoeba는 **Phase 2–4에는 더미 데이터를 올린 Amoeba 스테이징**을 사용하고, Go2Joy 인프라는 프로덕션에 사용하자고 제안합니다(PDF의 리스크 표와 동일). 인프라 구축이 기능 검증을 막지 않게 하기 위해서입니다.
- **상태.** 🟡 Amoeba 스테이징에는 Go2Joy 테넌트와 기본 지식베이스가 있습니다(`PLN-261001-Go2Joy-Guest-Login-Gate`의 K1 단계). 새 기능은 **아직 스테이징에 배포되지 않았습니다**(병합, 남은 SQL 18개 적용, 배포 대기). Go2Joy 인프라는 설치 패키지가 작성되었으나 실제로 실행한 적은 없습니다(6장 Phase 5).
- **산출물.** 적용 순서대로 정리한 SQL 목록(`RPT-261013-Go2Joy-Integration-Final.md` 3절), 설치 런북.
- **Go2Joy에 필요한 것.** 임시 스테이징 사용 동의, 이후 프로덕션 서버 지정.
- **장기적 가치.** "기능 검증"과 "인프라 구축"을 분리하면 인프라 때문에 파일럿이 늦어지지 않고, Go2Joy가 시스템을 직접 운영할 수 있음을 일찍 증명할 수 있습니다.

### C. 기술 자료와 API (R7–R12)

#### R7 — 인증 방식 문서
*세션/JWT/OAuth, 토큰 만료·갱신, 사용자 ID, 역할·소속 호텔 필드. 기한 10/14.*

- **판단.** Amoeba는 **Hotel Admin 내부 로그인 방식에 의존하지 않기로** 했습니다. Go2Joy 서버가 (사용자, 호텔, 역할, 시각)에 대한 HMAC 서명을 만들어 위젯에 전달하면 됩니다. 세션/JWT 구조를 공개할 필요가 없고 Hotel Admin 버전과 무관하며, 비밀 값이 서버에 있어 위조에도 견딥니다.
- **상태.** ✅ identify v2 계약이 구현되었고 면밀히 검증되었습니다.
  - 서명 문자열 `userId|hotelSn|role|iat[|province]`(테넌트별 비밀 키 HMAC). 유효한 역할은 `manager`, `receptionist`, `internal`. 호텔 이름·코드는 함께 전달되지만 서명 대상이 아니며(표시 전용) 시·도는 보낼 때 서명에 포함됩니다.
  - ±10분 시간 창. 서명이 틀렸거나 없거나 호텔·시·도가 바뀐 경우 모두 동일하게 거부합니다.
  - 사람·호텔·역할이 바뀌면 **세션 분리**, **서버 측 로그아웃**, **신원은 8시간 후 만료**(테넌트별 재정의 가능, 비상시 `0`으로 해제)되며 만료 시 위젯이 페이지 새로고침 없이 호스트에 재서명을 요청, 한 서명을 두 세션에 쓰는 **재전송 방지**, identify v1을 아예 거부하는 옵션.
  - 같은 브라우저를 다른 사람이 쓰면 개인정보 고지에 다시 동의해야 합니다.
- **산출물.** `apps/api/src/domain/embed/*`, `session/identity.util.ts`, PHP 서명 예제가 있는 SDK 가이드, 보안 테스트(`embed.service.v2.spec.ts`, `embed.service.rebind.spec.ts` 등): 미래 `iat`, ±600초 경계, 다른 테넌트의 서명, 재전송, 키 교체. 수정을 제거하면 테스트가 실패하도록 변이 테스트로 증명했습니다.
- **Go2Joy에 필요한 것.** 서버에서 서명, 로그인 후와 **호텔을 바꿀 때마다** `identify` 호출, 로그아웃 시 `ShopTalk.logout()` 호출, `identity-expired` 이벤트를 받아 재서명, 비밀 키 보관 위치 확인.
- **장기적 가치.** 다중 호텔 시스템의 가장 큰 위험인 호텔 간 데이터 유출을 막는 기반입니다. 서명 체계가 명확하면 새 채널(모바일 앱, 다른 페이지)도 재협상 없이 추가할 수 있습니다.

#### R8 — 기존 API 목록·명세
*Swagger/OpenAPI/Postman: 호텔, 객실·상품(시간제/숙박/일일 요금), 정책, 예약, 프로모션. 기한 10/14.*

- **판단.** Gate 3을 좌우합니다. 명세가 없으면 Amoeba는 어시스턴트가 실데이터로 답하는지 **검증할 수 없습니다.** 그래서 Amoeba가 거꾸로 접근했습니다. Phase 1의 "API 요구사항 초안"과 Phase 3의 "부족한 API 설계" 취지에 맞게 최소 API 계약을 직접 작성해, Go2Joy는 대조하고 "있다/없다"만 답하면 되게 했습니다.
- **상태.** 🔴 명세 미수령. ✅ 네 가지 주제의 계약 초안 v0(OpenAPI 3.0, 읽기 전용): 정책(취소/환불/체크인·아웃), 객실 요금(시간제/숙박/일일, 금액은 정수 VND), 예약, 정산. **절대 원칙: 어떤 요청에도 호텔 식별자 파라미터를 두지 않습니다.** 호텔은 서비스 인증 정보와, SharpTalk 서버가 서명된 신원으로 만든 헤더로 식별되며 API는 불일치 시 거부해야 합니다. 오류 모델, 호출 제한, 페이지네이션, 멱등성, 개인정보 최소화도 포함합니다.
- **산출물.** `docs/guide/API-REQ-Go2Joy-Partner-Data.openapi.yaml`, 2개 국어 설명서 `docs/guide/API-REQ-Go2Joy-Partner-Data.md`.
- **Go2Joy에 필요한 것.** 계약 초안을 기존 API와 대조해 있는 것과 없는 것 표시(R12), Swagger/Postman 전달.
- **장기적 가치.** 닫힌 파라미터의 읽기 전용 계약이 사용자의 말에서 호텔 ID를 받지 않으므로, **AI 모델이 속거나 착각해도 다른 호텔의 데이터를 읽을 수 없다**는 점이 구조적으로 보장됩니다. 호텔 사장이 어시스턴트가 금전 데이터를 다루도록 안심하는 이유입니다.

#### R9 — API 테스트 키
*스테이징 API 키, 호출 제한, 호출 IP 제한. 기한 10/16.*

- **판단.** 실제 통합 테스트에 필요하며, Go2Joy의 호출 제한이 타임아웃·재시도·캐시 설정을 좌우합니다.
- **상태.** 🔴 키 미수령. ✅ 계약 초안에 맞춰 실제 HTTP 클라이언트를 작성했고 로컬 가짜 서버로 검증했습니다.
  - GET만 호출, 시도별 타임아웃과 전체 시간 예산, 네트워크 오류/5xx 시 지터를 둔 1회 재시도, 서킷 브레이커
  - SSRF 방어(운영자가 허용하지 않으면 사설 주소/평문 HTTP 거부)
  - API가 돌려준 호텔이 신원의 호텔과 다르면 응답 폐기
  - 호텔 ID를 키에 포함한 30–60초 캐시, 조회 로그에 개인정보 미기록
  - 스위치 `PARTNER_DATA_ENABLED`, `PARTNER_API_MODE=mock|live`, 기본값은 **꺼짐**
- **산출물.** `apps/api/src/domain/partner-data/*`, 콘솔의 인증 정보 설정(제공자 `go2joy_partner_api`: 기본 주소, API 키, 선택적 서명 키).
- **Go2Joy에 필요한 것.** 스테이징 키, 호출 제한, 호출 IP 목록.
- **장기적 가치.** 오류 내성이 기본으로 들어 있습니다. 파트너 API가 느리거나 멈춰도 어시스턴트가 멈추지 않고 "추후 확인 + 사람 이관"으로 전환되어 파트너 장애 중에도 사용자 경험이 보호됩니다.

#### R10 — Hotel Admin 프런트엔드 정보
*운영 기준 버전(v0.4.1–v0.12.0 중), 프레임워크, 다국어 처리. 기한 10/14.*

- **판단.** 안내는 사용자가 보는 UI 버전과 맞을 때만 정확합니다. 버전이 틀리면 직원이 "어시스턴트를 따라 했는데 버튼이 없다"고 하는 흔한 원인이 됩니다(요구사항 FR-010).
- **상태.** ✅ 지식 문서마다 UI 버전 라벨(`ui_version`)을 붙입니다. 테넌트 설정 "참조 UI 버전"에 불일치 시 모드(안내 추가 / 문서 숨김 / 끔)가 있고, 불일치하면 모더레이션 후 답변에 **고정된 다국어 문장 한 줄**이 추가됩니다. 버전이 없는 문서는 콘솔에서 별도로 표시(플래그)되며 CSV 가져오기/내보내기에 버전 컬럼이 있습니다(이전 파일이 입력된 버전을 지우지 않음). 🟡 **버전 축은 미정**: 정책 파일은 현재 "v23.x"를, PDF는 "v0.4.1–v0.12.0"을 인용합니다. 코드는 **축과 무관하게** 비교합니다(공백 제거, 소문자화, 선행 `v` 제거 후 동일한지).
- **산출물.** `packages/types/src/common/kb-version.ts`, 컬럼 `kb_documents.ui_version`, `tenant_ai_config.kb_version_policy`(`sql/261016-kb-ui-version.sql`), 지식 관리·AI 설정 화면.
- **Go2Joy에 필요한 것.** 버전 축과 프로덕션 버전 확정, 문서군별 버전 제공 또는 릴리스 기준으로 Amoeba가 표기하도록 허용.
- **장기적 가치.** Hotel Admin이 새 버전을 내놓으면 어시스턴트가 **스스로** 낡았을 수 있는 문서를 인지하여, 조용히 틀린 안내를 하지 않습니다. 시간이 지나도 답변 품질을 유지하는 장치이며, 6개월 뒤에도 사용자가 신뢰하느냐를 좌우합니다.

#### R11 — 운영 데이터 샘플
*호텔 FAQ, CS 문의 유형·빈도(익명화), "Chat với khách"(고객과 채팅)·"Tin nhắn từ G2J"(G2J 발신 메시지) 데이터 구조, 최신 가이드. 기한 10/16.*

- **상태.** 🟡 기본 지식베이스가 있고 시험 사용도 마쳤습니다. 25개 주제 / 50개 베트남어·영어 문서, 7개 카테고리 그룹(Hotel Admin 정책 21개 주제를 화면 기반으로 작성 + 아직 파트너가 아닌 사람을 위한 **공개** 4개 주제: 로그인과 자주 나는 오류, 비밀번호 변경, 파트너 가입, Go2Joy 연락). "피드백 루프"는 기존에 있습니다. 시스템이 세 출처(이관이 잦은 질문 군집, 근거 없는 답변, 직원이 해결한 방식)에서 **지식 보강 작업**을 제안하고 담당자가 검토합니다. Go2Joy 데이터 입력은 대기 중입니다.

#### R12 — 신규 API 개발 협조

#### R14 — 파일럿 호텔 선정
*1차 적용 호텔 목록(수량 협의), 호텔별 연락처, 확대 순서 기준. 기한 10/21.*

- **상태.** ✅ **서명된 호텔 ID**를 기준으로 하는 파일럿 플래그(스스로 밝힌 이름·코드는 신뢰하지 않음). 테넌트별 목록, 호텔 하나 추가 / 목록 붙여넣기 / CSV 가져오기(미리보기 포함), 목록 밖 호텔은 **모델을 호출하기 전에 서버에서 차단**(대화 미저장, 비용 없음), 설정에 따라 위젯 숨김 또는 안내 표시, 로그인하지 않은 방문자는 별도 스위치, 호텔 추가는 다시 로그인하지 않아도 최대 약 60초 안에 반영, 모든 변경에 감사 로그.
- **산출물.** `domain/pilot/*`, 테이블 `tenant_pilot_hotels`와 컬럼 `tenants.pilot_access`(`sql/261016-tenant-pilot-hotels.sql`), 위젯 설정의 "호텔별 파일럿 범위" 카드, 통계의 Pilot 카드(6장 Phase 5).
- **Go2Joy에 필요한 것.** 1차 호텔 목록(서명에 담아 보내는 것과 같은 호텔 ID)과 확대 기준(11.4절에 제안).
- **장기적 가치.** "전부 켜기" 대신 실제 지표를 근거로 그룹별로 확대하면 매 단계에 품질 증거가 생기고, 다음 단계의 입소문을 만드는 첫 사용자들의 경험을 지킬 수 있습니다.

#### R15 — 배포·장애 대응 절차
*배포 승인 절차, 배포 시간대, 롤백 기준, 장애 연락망. 기한 10/21.*

- **판단.** 절차는 Go2Joy가 Hotel Admin을 배포하는 방식과 맞아야 합니다. Amoeba가 틀을 제공하고 Go2Joy가 결정 사항을 채웁니다.
- **상태.** ✅ 틀 작성 완료 — 13개 절의 런북: 역할, 외부로 나가는 데이터, 설치 패키지 전달과 체크섬 검증, 최초 설치, TLS/CSP, **배포 승인 체크리스트**(사전 백업, **SQL을 먼저 적용한 뒤 코드 배포**, "successfully started" 로그·컨테이너 가동 시간·새 라우트의 상태 코드(401 = 배포됨, 404 = 미배포, 502 = 중단)로 스모크 확인), 이미지 태그 기반 롤백과 SQL 되돌리기 안내(두 버전 사이에 되돌릴 수 없는 마이그레이션이 있으면 거부), 백업·복구 훈련, 모니터링, 장애 대응(개인정보 침해 72시간 신고 시계), DSAR과 보관, 키 관리(`CRED_ENC_KEY`는 함부로 교체하지 않음), Amoeba 지원 절차. 스크립트 테스트(97/97)와 임시 MySQL로 검증했으며 **실제 설치는 한 번도 실행하지 않았습니다.**

*호텔 직원 계정·대화 로그 처리 범위, 보관 기간, PDPL 동의 문구(필요 시). 기한 10/21.*

  - 동의 증적(부여/철회/버전)을 감사 로그에 저장하며 동의는 사람별로 받습니다.
  - 운영자용 DSAR 도구(이메일/전화/외부 ID로 방문자 조회, 내보내기, 삭제, 감사 로그), 데이터 삭제 시 신원 정보도 삭제.
  - 고객·감사 로그에 대한 확장 보관 정책(선택, 기본값 꺼짐).
  - DPIA 갱신(AI 사용 9가지, 기존 5가지에서 확대), 수탁 처리자(프로세서) 등록부 갱신(Notion, AmoebaTalk 허브, SMTP, jsDelivr, Go2Joy 호스팅 추가, 데이터 처리 계약 상태는 모두 "TBD"), 장애 연락처(빈칸, 명확히 표시).
- **산출물.** `packages/types/src/common/privacy-notice-copy.ts`, 개인정보 고지 화면, 콘솔의 DSAR 도구, `docs/guide/GUIDE-261013-Go2Joy-PDPL-Checklist.md`(Go2Joy·변호사가 정해야 할 사항), `docs/guide/AI-DPIA-GATE.md`, `docs/guide/PROCESSOR-REGISTER.md`.
- **알려진 공백(DPIA에 기록).** 직원용 AI 기능 두 가지(`agent_translate`, `agent_briefing`)가 개인정보를 가리지 않은 대화 텍스트를 AI 제공자에게 보냅니다. 은행 계좌·납세자 번호 마스킹은 미구현이며, 다른 프로필의 고지문에는 365일/미국 관련 템플릿 문구가 남아 있습니다.
- **Go2Joy에 필요한 것.** 보관 기간(Go2Joy 프로필 env는 `CONVERSATION_LOG_RETENTION_DAYS=180`, 시스템 기본값은 365. `vn_pdpl` 고지문이 이 값을 끼워 넣음 — 법적 값은 아님), 법적 근거, 컨트롤러 명칭, DPO, 베트남어 문구 검토자.
- **장기적 가치.** 데이터가 어디로 가는지 분명하고 투명한 준수 체계는 대기업과 법적 요건이 엄격한 호텔이 장기적으로 도입하기 위한 조건입니다. 엉성한 고지문은 Amoeba만이 아니라 Go2Joy의 법적 위험입니다.

*비로그인 응답 — 상세.* 각 어시스턴트에 "로그인 또는 가입만 안내" 옵션이 있습니다. 로그인하지 않은 방문자는 공개로 표시된 문서군에서만 답변을 받고, 그 밖의 질문에는 로그인·가입 페이지를 여는 버튼이 달린 짧은 안내가 나옵니다. 방문자로 계속 이용하거나 사람 연결을 요청할 수도 있습니다. 후속 질문에서 범위가 새던 문제는 수정되었고 컴파일 오류로 재발이 막혀 있습니다. 🟡 **사용법 FAQ는 현재 잠겨 있습니다**(공개는 계정 관련 4개 주제뿐). Go2Joy가 결정할 사항이기 때문입니다(10장 결정 5). **게이트 임계값은 실제 임베딩으로 측정하지 않았으며**, 보정 전까지 기본값은 일반 응답 모드를 유지합니다.

*접근 제어(RBAC) — 상세.*
- **역할별:** 지식 그룹에 공개 / 로그인한 파트너 / 관리자 전용 세 등급이 있고 검색 단계에서 강제됩니다(일반 모드 어시스턴트의 방문자 포함). 프런트 직원이 관리자 전용 주제를 물으면 사람 연결 버튼과 함께 "관리자 계정에 문의하세요"라는 안내를 받으며 **내용은 노출되지 않고** CS에 업무도 생기지 않습니다. 시나리오 버튼에 `manager` 대상을 지정할 수 있고 누르는 시점에 확인합니다. 재사용 답변은 등급별로 순위가 매겨져, 관리자의 답변이 프런트 직원에게 재생되지 않습니다.
- **호텔별:** 호텔·역할이 바뀌면 세션이 분리되고, 하나의 대화는 정확히 하나의 (사람, 호텔, 역할)에 대응하며 보고용으로 대화에 기록됩니다. 이전 호텔의 이력은 다음 호텔의 프롬프트에 들어가지 않습니다(실제 HTTP 테스트와 변이 테스트로 검증).

*조회 도구 — 상세.* 두 가지 모드가 있습니다. (a) **선조회**(기본값) — 시스템이 주제를 감지하고 데이터를 가져와 서버에서 데이터 블록을 만듭니다. (b) **도구 호출**(선택, 기본값 꺼짐) — 모델이 필요한 조회를 선택하지만 최종 답변은 쓰지 않습니다. 모든 호출은 동일한 역할 권한 검사, 금액 검사, 모더레이션을 통과합니다. 금액은 모델이 아니라 서버가 계산하며, 데이터와 숫자가 맞지 않는 답변은 "추후 확인 + 사람 이관"으로 낮춰집니다.

*격리 테스트 — 상세.* 다른 사람/다른 호텔/다른 역할 → 새 세션, 같은 사람·같은 호텔 → 분리 없음, 잘못된 서명은 아무것도 기록하지 않음. 8시간 후 만료 → 방문자로 취급하고 위젯이 호스트에 재서명을 요청. ±600초 창, 미래 또는 유효하지 않은 `iat`, 다른 테넌트의 서명, 두 세션 간 재전송, 키 교체, 역할·호텔 ID 변조. 지식 등급 격리, 재사용 격리, 호텔 간 파트너 데이터 격리(다른 호텔의 미끼 레코드는 절대 반환되지 않음). 품질 규칙: 모든 보안 수정은 **수정을 제거하면 테스트가 실패함**으로 증명했습니다.

*품질 평가 — 상세.*
- *이관율, 자체 해결, 거절 사유, 모더레이션:* 통계의 Pilot 카드(Phase 5).
- *정확도:* 골든 질문 세트를 기대·금지 내용으로 채점하며, **대상**과 **게이트 기대값** 두 필드를 추가해 방문자·관리자 게이트 동작도 채점합니다.
- *방문자 게이트:* 지식 관리의 "Thử với tư cách…"("…로 시험하기") 기능으로 네 가지 관점(비로그인 방문자, 로그인한 파트너, 프런트, 관리자)을 시험하고 게이트의 결정, 임계값 대비 신뢰도, 등급이 표시된 일치 분류, 방문자가 실제로 읽을 답변을 확인합니다. `npm run gate:calibrate` 명령은 라벨이 있는 질문 세트로 임계값을 고르며(유출이 없는 쪽에 치우침) **가짜 임베딩뿐이면 경고를 출력하고 종료 코드 3으로 끝납니다.**
- 실제 모델·임베딩: 미시험.

*성능·보안 — 상세.* **보안:** 변조·재전송·만료는 시험 완료(위). 로그와 모더레이션 기록의 개인정보 마스킹이 있습니다(베트남 전화번호, 이메일, 카드 번호 등). **성능:** 모든 턴이 단계별 시간(분류, 검색, 생성, 모더레이션)을 트레이스와 `/metrics` 히스토그램에 기록합니다. **실제 모델로는 아직 측정하지 않았습니다.** 시스템에 **스트리밍이 없어** NFR-001의 "첫 토큰 2초 이하" 기준은 측정할 수 없습니다. Amoeba는 이를 "첫 피드백까지의 시간"으로 재정의하거나 스트리밍을 구현하자고 제안합니다(출력 전 모더레이션 요구와 충돌).

*운영 매뉴얼·교육 — 상세.* **CS / Sales Admin용 Go2Joy 운영 매뉴얼**(베트남어 + 영어 요약): 13개 장, 실습 10개, 한 장짜리 요약표, 용어집, 12문항 퀴즈, 실제 콘솔 화면 27장(샘플 데이터). 인용한 모든 라벨을 실제 UI와 대조했습니다(굵게/기울임 685개를 로케일 파일에서 조회). 독립적인 두 검토자가 문제를 찾았고 수정하거나 기록했습니다. 발견된 제품 결함(역할 이름 변경, 오류 시 조용히 실패하던 수락 버튼, 직원 표시 이름 누락, 직급 번역, 파트너 데이터 중단 시 "낮은 신뢰도"로 표시되던 알림, IVY 번호가 있던 연락 카드 등)은 **수정되었습니다.**

## 11. 사용자 가치와 장기적 의미

### 11.1 사용자 그룹별로 얻는 것

| 그룹 | 경험하는 것 | 이를 보장하는 장치 (이미 코드에 있음) |
|---|---|---|
| **호텔 관리자** | 자기 호텔 맥락에 맞는 질문·답변, 금전·권한 주제는 본인에게만 전달, 호텔을 바꿔도 어시스턴트가 이전 호텔을 "착각해 기억"하지 않음, 이후에는 자기 호텔의 실데이터 | 서명된 신원, 그룹 단위 접근 등급, 세션 분리, 읽기 전용 데이터 계약 |
| **프런트 직원** | 일상 업무 질문에 짧고 단계별로 굵은 글씨·목록이 있는 답변, 관리자 주제를 물으면 틀린 답 대신 분명한 안내, 프런트 공용 PC 안전 사용: 다음 사람이 이전 사람의 대화를 보지 못함 | 짧고 구조화된 답변 규칙, "관리자에게 문의" 안내, 서버 측 로그아웃, 사람별 동의 |
| **아직 파트너가 아니거나 로그인하지 않은 사람** | 로그인, 비밀번호 변경, 파트너 가입 방법을 물을 곳이 있고, 올바른 페이지로 안내되며, 내부 콘텐츠는 보지 못함 | 방문자 게이트, 공개 4개 주제, 언어별 로그인·가입 버튼 |
| **Go2Joy CS / Sales Admin** | 호텔·역할·시·도와 "서명됨" 여부를 한눈에 확인, 자기 팀 업무만 자기 지역 기준으로 수신, 아무도 받지 않으면 알림, 팀을 잘못 골랐을 때 한 번에 수정, 매뉴얼과 연습 문제 | 대화 헤더, "근무 중" 상태, 라벨 + 지역 기준 담당자 선택, "미접수" 일괄 점검, 메모가 남는 팀 이관, 대기열 카운터, 매뉴얼 |

### 11.2 장기적 영향이 있는 이유

1. **신뢰가 장기 사용을 결정합니다.** 호텔 간 데이터 유출이나 금액 관련 오안내가 한 번만 있어도 호텔 사장은 어시스턴트를 포기합니다. 그래서 대부분의 노력이 사용자에게는 보이지 않지만 "중대한 일은 절대 틀리지 않는다"는 느낌으로 전해지는 부분에 들어갔습니다. 서버의 강한 격리, 닫힌 API 파라미터, 시스템이 계산하는 금액, 답변 전 숫자 검증, 감사 가능한 사유가 있는 거절입니다.
2. **오래 유지되는 품질.** 지식의 UI 버전 표기와 불일치 경고, 답이 없던 질문을 새 지식으로 바꾸는 피드백 루프, 사용자가 알아채기 전에 품질 저하를 찾아내는 골든 세트와 게이트 보정 도구.
3. **사용자를 막다른 길에 두지 않습니다.** 모델이나 벡터가 멈추면 사용자 언어로 별도 안내("확인 후 직원이 도와드리겠습니다"), 근거가 있으면 키워드로 답변, 다시 시도 / 사람 연결 버튼. 업무 시간 외에는 이메일을 받아 침묵 대신 회신합니다. 아무도 받지 않으면 시스템이 스스로 수신자를 넓힙니다.
4. **측정할 수 있어야 개선할 수 있습니다.** 호텔·역할·일자별 수치, 올바르게 정의한 자체 해결률, 이관 사유, 침묵 호텔은 어떤 지식을 먼저 써야 하는지, 어느 그룹이 쓰지 않는지, 어느 확대 단계가 안전한지 알려 줍니다.
5. **재작업 없는 확대.** 서명된 신원, 호텔 격리, 접근 등급, 읽기 전용 데이터 계약, 호텔 단위 플래그와 측정은 Stage 2(호텔별 투숙객 예약과 프런트)의 전제 조건과 같습니다. Stage 1에서 한 번 만들어 이후 단계에서 계속 씁니다.
6. **낮은 운영 비용, 적은 인원으로 운영 가능.** 시스템이 스스로 라우팅하고 재알림하고 경고하며 매뉴얼이 있어 전담 인력이 필요 없습니다. 인력이 적고 비용 규율이 강하다는 Go2Joy의 전략적 신호와 맞습니다.

## 12. 분명히 밝혀 두는 한계

1. **실제 파트너 API:** 명세·키가 없어 모든 조회를 샘플 데이터와 가짜 서버로만 시험했습니다. 도구 호출 모드는 가짜 Anthropic 서버로만 시험했고, 베트남어·한국어 도구 선택 품질은 측정하지 않았습니다(예: "다음 토요일" 같은 상대 날짜는 잘못 해석될 수 있음).
2. **방문자 게이트 임계값:** 실제 Voyage + Qdrant로 측정하지 않았습니다. 가짜 임베딩에서 관찰한 바로는 게이트가 주제별로 닫히지 않습니다(관리자 전용 내용을 묻는 방문자도 통과). 그래서 기본값을 일반 응답 모드로 두고, 켜기 전에 스테이징에서 `gate:calibrate`를 실행해야 합니다. 또한 Voyage가 작동하지만 범위 안의 벡터 결과가 없을 때, 일치 문서 수에서 나온 신뢰도가 0.62 이상이 될 수 있으며 보정 도구가 이 경우를 경고합니다.
3. **설치:** `docker build`를 실행하지 않았고, Linux 시험 설치도 `nginx -t`도 하지 않았습니다. 백업·복구는 임시 MySQL과 가짜 Qdrant로만 검증했습니다.
4. **외부 서비스:** 실제 Slack/SMTP와 실제 Sentry는 시험하지 않았고, 실제 Hotel Admin 페이지에서도 검증하지 않았습니다. 위젯의 일부 경로(연락 카드, 동의 배너, 전송 실패 후 다시 시도 / 사람 연결 버튼)는 단위·DOM 테스트로만 확인했습니다.
5. **번역과 법무:** es/ko/ja/zh는 키가 모두 있는지만 확인했고, 베트남어는 원어민 검토가 필요하며, PDPL 문구는 초안입니다.
6. **규모:** 실제 트래픽으로는 시험하지 않았습니다(파일럿 보고서용으로 대화 20만 건만 시험).
7. **병합 전 Amoeba의 미결정 사항:** Sales Admin은 주문 메뉴가 보이지만 엔드포인트에 운영 라벨이 필요해 403이 반환됩니다. 약 3 MB의 Pretendard 폰트 번들이 저장소에 추가되었고(OFL 라이선스) 확인이 필요합니다.
8. **배포 시 운영 중인 테넌트의 동작 변화:** 신원 수명 8시간, 세션 분리, 사람별 동의, 서명된 호텔이 있는 대화의 직원 답변을 재사용 저장소에 저장하지 않음, 라우팅 설정이 있는 테넌트에서 "미접수" 일괄 점검 기본 활성화, 알림 이메일 제목 접두사 변경, 기본 IVY 연락처 제거. 자세한 내용은 종합 RPT 4절과 PR 설명을 참조하시기 바랍니다.

### 13.2 Amoeba

1. 브랜치 병합, 스테이징에 남은 SQL 18개를 순서대로 적용(`261001-guest-login-gate.sql`은 10/07 적용 완료), 배포, 스모크 테스트와 `PLN-261001`의 K2–K5 단계 실행(10/15경).

4. Go2Joy와 함께 Linux 서버에서 프로덕션 패키지 설치 리허설, `nginx -t` 확인, 실제 백업·복구.
