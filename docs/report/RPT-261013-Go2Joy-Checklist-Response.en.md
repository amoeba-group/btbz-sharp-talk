## 1. Executive summary

### 1.1 Conclusion

Amoeba's share of Stage 1 is **built almost completely at the source-code level and verified in Amoeba's local environment**: a signed identity bridge (SSO), role-based content access for Managers and Front-desk staff, a signed-out visitor gate, a per-hotel pilot flag, CS / Sales Admin routing by team and region, a partner-data lookup module, pilot metrics, PDPL compliance (draft), a deployment package for Go2Joy's own infrastructure, and a Vietnamese operations manual.

What **cannot be finished without Go2Joy's inputs**, in order of schedule impact:

1. The partner API specification and keys (R8, R9) — these decide Gate 3, "answers with live data".
2. Hotel Admin and Super Admin accounts (R1, R2) — these decide the role-based menu map and the isolation UAT.
3. Signing identify on Go2Joy's server and calling it again on hotel switch and sign-out (R7).
4. The legal owner of the PDPL notice (R16), the pilot hotel list (R14), and the hosting location (R6).

### C. Technical documents and APIs (R7–R12)

#### R7 — Authentication spec
*Session/JWT/OAuth, token expiry and refresh, user ID, role and hotel fields. Due Oct 14.*

- **Assessment.** Amoeba chose **not to depend on Hotel Admin's internal login mechanism**: Go2Joy's server only needs to create an HMAC signature over (user, hotel, role, time) and hand it to the widget. This does not require Go2Joy to reveal session/JWT internals, does not depend on the Hotel Admin version, and resists forgery because the secret stays on the server.
- **Status.** ✅ the identify v2 contract is implemented and heavily tested:
  - Signed string `userId|hotelSn|role|iat[|province]` (HMAC with a per-tenant secret); valid roles `manager`, `receptionist`, `internal`; hotel name and code travel along but are not signed (display only); the province is signed when sent.
  - ±10-minute time window; a wrong, missing, hotel-swapped or province-swapped signature is rejected identically.
  - **Session fork** when the person, hotel or role changes; **server-side sign-out**; **identity expires after 8 hours** (per-tenant override; `0` as an emergency off-switch) and the widget tells the host to re-sign without a page reload; **replay protection** for a signature used on two sessions; an option to reject identify v1 entirely.
  - A different person on the same browser must accept the privacy notice again.
- **Output.** `apps/api/src/domain/embed/*`, `session/identity.util.ts`; the SDK guide with a PHP signing sample; security suites (`embed.service.v2.spec.ts`, `embed.service.rebind.spec.ts`…): future `iat`, the ±600-second boundary, another tenant's signature, replay, key rotation; each fix is proven by turning the test red when the fix is removed (mutation testing).
- **Needed from Go2Joy.** Sign on the server; call `identify` after login and on **every hotel switch**; call `ShopTalk.logout()` on sign-out; listen for the `identity-expired` event to re-sign; confirm where the secret is stored.
- **Long-term value.** The foundation against cross-hotel data leaks — the biggest risk of a multi-hotel system. A clear signing mechanism also lets new channels (mobile app, other pages) be added without renegotiation.

#### R8 — Existing API list and specs
*Swagger/OpenAPI/Postman: hotels, rooms/products (hourly, overnight, daily), policies, bookings, promotions. Due Oct 14.*

- **Assessment.** This decides Gate 3. Without a spec, Amoeba **cannot** test the assistant answering with live data. So Amoeba worked in reverse: it wrote a minimal API contract itself (in the spirit of Phase 1 "draft API requirements" and Phase 3 "design missing APIs") so that Go2Joy only has to compare it and answer "exists / does not exist".
- **Status.** 🔴 no spec received. ✅ draft contract v0 (OpenAPI 3.0, read-only) for four topics: policies (cancellation / refund / check-in-out), room rates (hourly / overnight / daily, amounts as integer VND), bookings, settlement. **Hard rule: no hotel-identifier parameter appears in any request** — the hotel is identified by the service credential plus a header that SharpTalk's server builds from the signed identity; the API must reject a mismatch. It also includes an error model, rate limits, pagination, idempotency, and personal-data minimisation.
- **Output.** `docs/guide/API-REQ-Go2Joy-Partner-Data.openapi.yaml` and the bilingual explanation `docs/guide/API-REQ-Go2Joy-Partner-Data.md`.
- **Needed from Go2Joy.** Compare the draft contract with existing APIs; say which exist and which are missing (R12); send the Swagger/Postman.
- **Long-term value.** A read-only contract with closed parameters that never accepts a hotel ID from the user's words guarantees, at the architecture level, that **even if the AI model is fooled or mistaken, it still cannot read another hotel's data** — which is what makes hotel owners comfortable letting the assistant touch money-related data.

#### R9 — API test credentials
*Staging API keys, rate limits, caller IP restrictions. Due Oct 16.*

- **Assessment.** Needed for real integration tests; Go2Joy's rate limits decide how timeouts, retries and caching are configured.
- **Status.** 🔴 no keys yet. ✅ the real HTTP client is written against the draft contract and tested against a local fake server:
  - GET only; per-attempt timeout and total budget; one jittered retry on network error/5xx; circuit breaker;
  - SSRF protection (private addresses / plain HTTP rejected unless the operator allows them);
  - a response is dropped when the hotel the API returns differs from the hotel in the identity;
  - a 30–60-second cache with the hotel ID in the key; lookup logs hold no personal data.
  - Switches `PARTNER_DATA_ENABLED`, `PARTNER_API_MODE=mock|live`; **off** by default.
- **Output.** `apps/api/src/domain/partner-data/*`; credential settings in the console (provider `go2joy_partner_api`: base URL, API key, optional signing secret).
- **Needed from Go2Joy.** Staging keys, rate limits, caller IP list.
- **Long-term value.** Built-in fault tolerance: a slow or down partner API does not freeze the assistant but turns into "confirm later + hand off to a person", protecting the user experience during a partner incident.

*Access control (RBAC) — detail.*

## 11. Value for users and long-term impact

### 11.1 What each group of users gets

| Group | What they experience | Mechanism that guarantees it (already in the code) |
|---|---|---|
| **Hotel Managers** | Questions answered in the context of their own hotel; money and permission topics reach only them; after switching hotels the assistant does not "remember the old hotel by mistake"; later, real data for their hotel | Signed identity, group-level access tiers, session fork, a read-only data contract |
| **Front-desk staff** | Daily how-to questions answered briefly, step by step, with bold text and lists; asking a Manager topic is met with clear directions instead of a wrong answer; a shared front-desk PC is safe: the next person does not see the previous person's conversation | Short structured-answer rules, the "ask your Manager" reply, server-side sign-out, per-person consent |
| **People who are not partners / not signed in** | A place to ask how to sign in, change a password, register as a partner; they are pointed to the right page; no internal content is revealed | Visitor gate, 4 public topics, sign-in / registration buttons per language |
| **Go2Joy CS and Sales Admin** | See hotel / role / province and "signed" or not at a glance; only receive their own team's work for their own region; are alerted when nobody takes a conversation; a wrongly chosen team is fixable in one action; have a manual and exercises | Conversation header, "On duty" presence, label + region selection ladder, "unclaimed" sweep, re-route with a note, queue counters, the manual |
| **Go2Joy management** | See how much the assistant resolves, at which hotels, and why it hands off; have data to decide on expansion | The Pilot card, CSV export, silent-hotel list, golden set + gate simulation |

### 11.2 Why this has long-term impact

1. **Trust decides long-term use.** One cross-hotel data leak or one wrong money instruction is enough for a hotel owner to abandon the assistant. Most of the effort therefore went into things users do not see but feel as "never wrong about anything serious": hard isolation on the server, closed API parameters, money computed by the system, a figure check before answering, and refusals with auditable reasons.
2. **Quality that lasts.** UI-version stamping with a mismatch warning; a feedback loop that turns unanswered questions into new knowledge; a golden set and a gate-calibration tool that detect degradation before users notice it.
3. **Users are never left stuck.** When the model or vector backend is down: a distinct notice in the user's language ("we will confirm and a person will help"), keyword answers when grounded, Retry / Talk-to-a-person buttons. After hours: ask for an email so we can reply instead of staying silent. Nobody takes it: the system widens the recipients itself.
4. **What is measured can be improved.** Numbers by hotel / role / day, a properly defined self-resolution rate, handoff reasons and silent hotels show which knowledge to write next, which groups are not using it, and which expansion wave is safe.
5. **Expansion without rework.** Signed identity, hotel isolation, access tiers, the read-only data contract, the per-hotel flag and measurement are exactly the prerequisites of Stage 2 (guests booking and front-desk staff per hotel): built once in Stage 1, reused in later stages.
6. **Low operating cost, a lean team can run it.** The system routes, reminds and alerts by itself, with a manual; it needs no dedicated staff — matching Go2Joy's strategic signals about a lean team and cost discipline.

- (b) the correct self-resolution rate has reached the agreed threshold;
- (c) silent hotels are below the agreed threshold;
- (d) there is no unresolved serious incident.

## 12. Limits we state plainly

1. **Real partner API:** no spec or keys yet; every lookup has been tested only against sample data and a fake server; tool-calling mode has been tested only against a fake Anthropic server; tool-selection quality in Vietnamese / Korean is unmeasured (a relative date such as "next Saturday" can be misread).
2. **Visitor-gate threshold:** not measured with real Voyage + Qdrant. Observed with fake embeddings: the gate does not close by topic (even a visitor asking Manager-only content is let through) — which is why the default stays at normal answering and `gate:calibrate` must be run on staging before enabling it. In addition, when Voyage runs but returns no in-scope vector hit, the confidence derived from the number of matching documents can be ≥ 0.62; the calibration tool warns about this case.
3. **Installation:** `docker build` has not been run, no trial install on Linux, `nginx -t` not run; backup/restore tested only against a scratch MySQL and a fake Qdrant.
4. **External services:** real Slack/SMTP and real Sentry not tested; not tested on the real Hotel Admin page; some widget paths (the contact card, the consent banner, the Retry / Talk-to-a-person buttons after a failed send) are covered only by unit / DOM tests.
5. **Translations and legal:** es/ko/ja/zh have only been checked for complete keys; the Vietnamese needs a native-speaker review; the PDPL text is a draft.
6. **Volume:** not tested with real traffic (200 thousand conversations were tried for the pilot report).
7. **Amoeba's open decisions before merging:** Sales Admin sees an Orders menu but the endpoint needs the operations label (returns 403); a Pretendard font bundle of about 3 MB has been added to the repo (OFL licence) and needs confirmation.
8. **Behaviour changes for running tenants on deploy:** an identity lifetime of 8 hours; session forking; per-person consent; staff answers for signed-hotel conversations are no longer stored in the answer-reuse store; the "unclaimed" sweep is on by default for tenants with routing configuration; a new alert-email subject prefix; the default IVY contact removed. Details: the consolidated RPT, section 4, and the PR description.
