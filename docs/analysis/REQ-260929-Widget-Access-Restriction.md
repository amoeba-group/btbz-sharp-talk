# REQ-260929 — 샵톡 위젯 노출 제한: 지정 IP·URL·기간·사용자

- 요청(2026-09-29): "샵톡 위젯을 사용자 설정에서 지정한 **IP 또는 정해진 URL** 에서만 보이는 기능 구현 필요

### 1-1. 지금 상태에서 가장 중요한 두 가지

**① 콘솔 문구가 이미 앞서 있다.** 허용 도메인 설명은 한국어로 *"이 도메인에서만 위젯이 뜹니다"* 라고
쓰여 있는데, 서버는 관측 모드라 실제로는 **모든 도메인에서 뜬다.** 이번 요구사항은 새 기능이기도 하지만,
**이미 한 약속을 지키는 일**이기도 하다.

**② 서버가 거절해도 위젯은 사라지지 않는다.** `useSession`의 ensure 실패 경로는

```ts
.catch(() => {
  /* offline / backend not running — widget still renders */
});
```

이고, 런처는 `localStorage`에 캐시된 테마로 **ensure 응답 전에 이미 그려진다**. 즉 403을 돌려주는
것만으로는 "보이지 않게"가 성립하지 않는다 — 버튼은 그대로 뜨고 누르면 동작만 안 되는,
FIX-260916과 같은 계열의 "고장난 것처럼 보이는" 상태가 된다. **숨김은 별도의 경로로 설계해야 한다.**

## 2. 갭 분석 — 요구사항별로 무엇이 필요한가

| # | 요구 | 판정 | 필요한 것 |
|---|---|---|---|

| G2 | 지정 **IP에서만** 노출 | **신규** | `tenants`(또는 신규 테이블)에 IP/CIDR 허용목록 + 판정 지점에서 XFF 첫 홉과 대조. IPv4/IPv6·CIDR 파서 필요 |
| G3 | **테스트 기간** 한정 | **신규** | 제한 자체의 유효창(`starts_at`/`ends_at`, 타임존 명시). 만료 시 **자동으로 원래 상태로** 복귀 |

| G5 | 거절 시 **안 보이게** | **신규** | 로더가 **마운트 전에** 판정을 묻고, 거절이면 iframe 자체를 붙이지 않는 경로 |

## 3. 설계 선택지

### 3-1. 판정 지점 — **로더 선판정(권장)** vs ensure 플래그

| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **A. 로더 선판정** | `embed.js`가 마운트 전에 `GET /public/widget/visibility?shop=…`(브라우저에서 호출 → 서버가 **실 IP·Origin·Referer**를 본다) → `visible:false`면 **iframe을 아예 만들지 않음** | 깜빡임 없음, 흔적 0(런처도 안 그려짐), IP를 볼 수 있는 유일한 지점 | 요청 1회 추가(캐시로 완화) |
| B. ensure 응답 플래그 | 지금처럼 마운트하고 `session/ensure`가 `hidden:true`를 주면 위젯이 스스로 사라짐 | 신규 엔드포인트 없음 | **런처가 한 번 그려졌다 사라진다**(캐시 테마로 선렌더) — 사용자에겐 깜빡임/버그로 보임 |

→ **A 권장.** B는 A의 보조로만(오래된 로더가 깔린 스토어 대비).

### 3-2. 캐시 주의

로더는 런처 기하를 `ivy:launcher:{shop}`에, 위젯은 테마를 `ivy_theme:{shop}`에 캐시한다.
판정 결과를 같은 방식으로 캐시하면 **기간이 끝나도 계속 숨겨지거나, 차단이 늦게 걸린다.**
판정은 짧은 TTL(예: 60초)로만 캐시하고, 만료·해제는 즉시 반영되게 한다.

### 3-3. 이것은 접근 제어가 아니라 **노출 제어**다 (반드시 합의할 것)

- **Origin/Referer는 브라우저가 보내는 값**이고 `curl`은 무엇이든 보낼 수 있다 — `embed-origin.util.ts`
  첫 주석이 이미 못 박아 둔 사실이다.
- **IP는 XFF 첫 홉**이며, 엣지 프록시가 세팅한다는 신뢰 모델에 의존한다.

따라서 이 기능은 **"지정 환경 밖에서는 위젯이 뜨지 않는다"**를 보장하지만,
**"데이터가 새지 않는다"**를 보장하지는 않는다. 후자가 필요하면 세션 발급·주문/지식 조회까지
같은 판정을 걸어야 하며(= 성능·예외 처리 범위가 커진다), 그건 별도 결정이다(§4 D4).

## 4. 미결 결정

| # | 결정 | 선택지 | 제안 |
|---|---|---|---|
| **D1** | **"정해진 사용자"의 정의** | ⓐ IP로 갈음(사무실·테스터 회선) ⓑ 스토어 **로그인 고객 이메일 허용목록** ⓒ **초대 링크/키**(`?st_access=KEY` 1회 방문 후 쿠키) | **ⓐ+ⓒ** — IP는 사무실, 키는 외부 테스터. ⓑ는 로그인 전에는 판정 불가라 "로그인해야 위젯이 보인다"는 이상한 순서가 된다 |
| **D2** | URL 매칭 단위 | ⓐ 도메인(현행 매처 재사용) ⓑ 도메인+**경로 프리픽스**(`/collections/test*`) | **ⓑ** — "정해진 URL"이라는 표현에 더 맞고, 매처에 경로 규칙만 더하면 된다 |
| **D3** | 규칙 조합 | ⓐ **OR**(IP 또는 URL 중 하나만 맞아도 노출) ⓑ AND(둘 다) | 요청 문구가 "IP **또는** URL"이므로 **ⓐ OR**. 단 기간은 항상 AND |
| **D4** | 차단 범위 | ⓐ **노출만**(위젯 안 뜸, API는 그대로) ⓑ 노출+**세션 발급까지 거절** | **ⓑ 권장** — 이왕 판정하는 김에 `session/ensure`에도 같은 규칙을 걸면 "안 보이는데 API는 열려 있음"을 피한다. 단 ⓑ는 §3-3의 한계는 그대로 |
| **D5** | 기간 종료 후 | ⓐ **제한 해제**(전체 공개로 복귀) ⓑ 전면 차단 유지 | **ⓐ** — "테스트 기간" 문구의 자연스러운 해석. 콘솔에 종료일과 종료 후 동작을 명시해 오해를 없앤다 |
| D6 | 적용 범위 | 테넌트 단위 / 에이전트·채널 단위 | **테넌트 단위**(이번 목적은 테스트 통제) |

## 5. 사용자 흐름 (TO-BE, D1=ⓐ+ⓒ · D2=ⓑ · D3=OR · D5=ⓐ 가정)

1. 콘솔 **설정 > 임베드 · SDK > "노출 제한(테스트 모드)"**: 켜기 · 허용 IP/CIDR · 허용 URL(도메인+경로) ·
   시작/종료 일시(테넌트 타임존) · 초대 키 발급
2. 저장 즉시 적용. 콘솔에 **"지금 이 설정이면 ○○에서만 보입니다"** 요약 + 종료일 안내
3. 방문자: 규칙에 맞으면 평소대로, 아니면 **위젯이 존재하지 않는 것처럼** 아무것도 뜨지 않음
4. 테스터: 초대 링크 1회 방문 → 쿠키 발급 → 이후 같은 브라우저에서는 어디서든 노출
5. 종료 일시가 지나면 **자동으로 제한 해제**(콘솔 배지도 해제 표시)

## 6. 제약·전제

| # | 내용 |
|---|---|
| C1 | 판정은 브라우저가 주는 Origin/Referer와 XFF IP에 기반 — **위조 가능**(§3-3). 감사·규제 목적의 접근 통제로 쓰면 안 된다 |
| C2 | **숨김은 로더에서** 이뤄져야 한다. 서버 403만으로는 런처가 그대로 뜬다(§1-1 ②) |
| C3 | 이미 설치된 구 로더는 선판정 요청을 보내지 않는다 → ensure 플래그(B안) 폴백이 필요하고, 그 경우 깜빡임을 감수한다 |
| C4 | 사내망/모바일 통신사 IP는 자주 바뀐다 — IP만으로 테스터를 묶으면 현장에서 막힌다(D1에서 키 병행을 권하는 이유) |
| C5 | IPv6·CIDR 표기 파싱 필요. 잘못된 입력은 **저장 시점에 거절**한다(런타임에 조용히 통과시키지 않는다) |
| C6 | 판정 캐시 TTL은 짧게(§3-2). 기간 만료가 즉시 반영돼야 한다 |
| C7 | 관측 모드(`EMBED_ORIGIN_ENFORCE`)와의 관계 정리 필요 — 이번 기능이 집행을 켜는 첫 소비자다 |
