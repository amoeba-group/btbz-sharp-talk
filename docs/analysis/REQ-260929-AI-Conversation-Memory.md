## 2. 원인 분석 (코드 실측)

### 원인 A — 모델에 현재 메시지 한 줄만 보낸다 (**근본 원인**)

AI 호출 세 곳 모두 `messages` 배열에 **현재 발화 하나만** 넣는다.

```ts
// rag.service.ts answer()                 — messages: [{ role: 'user', content: query }]
// rag.service.ts answerWithoutKnowledge() — messages: [{ role: 'user', content: query }]
// rag.service.ts classifyIntent()         — messages: [{ role: 'user', content: query }]
```

`answer()`의 주석이 이 설계를 명시한다: *"The model still sees just `query` (FIX-260806 A2)."*
FIX-260806 A2는 **검색어**에만 이전 고객 발화 2개(각 200자)를 붙였다(`retrievalQueryFor`).
검색 결과(어떤 KB 문서를 가져올지)는 좋아졌지만 **답변을 쓰는 모델은 대화를 전혀 모른다.**
그래서 이 시스템의 AI는 매 턴이 첫 대화다. 이번 결함은 skyliving 한 곳의 문제가 아니라
**모든 테넌트·모든 채널의 구조적 결함**이다. 위젯(`chat.controller`)과 메신저 릴레이·이메일
(`messenger-ingest.service`)이 모두 같은 `handleUserMessage()`를 지난다. 최근 60일 동안 고객 발화가
3턴 이상인 대화 199건이 전부 이 조건에서 응답을 받았다.

"요청한 사항을 기억"하려면 모델이 **자기가 직전에 한 질문(assistant 턴)** 을 봐야 하고, "답변을 기억"하려면
**고객의 이전 발화(user 턴)** 를 봐야 한다. 지금은 둘 다 전달되지 않는다.

### 원인 B — 의도 분류기도 맥락이 없어 '답변'을 '잡음'으로 오분류

`classifyIntent()`는 "벽걸이", "1. 김익용", "예약 진행"을 **질문이 없는 단독 문장**으로 본다.
직전에 AI가 "종류를 알려주세요"라고 물었다는 사실을 모르므로 `unintelligible`/`other`로 떨어진다.
conf ≥ 임계값이면 `answerWithoutKnowledge()`(비질문 분기)로 빠져 **KB도 이력도 없이**
"이해하지 못했어요"를 답한다(17703).

### 원인 C — 분류기가 테넌트 업종을 몰라 본업을 out_of_scope로 판정

분류 프롬프트는 "the shopper… this shop cannot answer (weather, exchange rates, news)"로
**쇼핑몰을 가정**한다. 청소·방역 서비스 테넌트의 "에어컨 청소 예약"이 out_of_scope(0.85)로 판정돼
**KB 검색 없이** 거절했다(17685). 정작 KB에는 `벽걸이 에어컨 청소 가격`(doc 3335)과
`서비스 예약 방법 및 절차`(doc 3340)가 있다. 비질문 분기가 "검색 전에" 배치된 것
(PLN-260813 P2)은 인사말에는 맞지만, 오분류된 진짜 질문은 KB를 한 번도 보지 못한다.

### 원인 D — PII 치환 토큰이 응답에 노출

AI로 가는 텍스트는 `scrubPii()`로 `[PHONE]`/`[EMAIL]`/`[ADDR]` 등으로 치환된다(PRV Stage 5 — 유지해야 함).
모델에게 토큰의 의미를 알려주지 않아서, 모델이 토큰을 그대로 받아 적었다. 이력을 붙이면 토큰이 더 자주
등장하므로 **A를 고칠 때 같이 고쳐야 한다.**

### 원인 E (관련 갭) — "예약 진행"이 아무에게도 전달되지 않는다

AI는 "담당 직원이 24 영업시간 이내에 확정해 드립니다"라고 안내하지만, 이 대화는 `ai_active` 상태 그대로다.
핸드오프도, 티켓도, 알림도 생기지 않았다. **기억 문제를 고쳐도 확정된 예약이 사람에게 닿지 않는다.**
이번 요구의 직접 범위는 아니지만 같은 사용자 흐름의 끝이므로 PLN에 결정 항목으로 올린다.

### 부수 관찰 — 답변 재사용(Track C)

`answerReuse.lookup()`은 **현재 문장만으로** 이전에 검증된 답을 재생한다(LLM 미호출). 원인 A를 고쳐도,
"예약 진행"처럼 맥락에 기대는 짧은 후속 발화가 재사용에 걸리면 이력을 무시한 고정 답이 나간다.
A를 고칠 때 재사용 조건도 함께 좁혀야 한다.

## 3. TO-BE

1. AI는 같은 대화의 **최근 턴(고객·AI·상담원)** 을 보고 답한다. 이미 받은 정보는 다시 묻지 않고,
   **받은 것을 확인하고 빠진 것만** 묻는다.
2. 짧은 답변("벽걸이", "2대", "예약 진행", "1. 김익용")은 **직전 질문에 대한 답**으로 분류·처리된다.
3. 테넌트 본업 질문은 분류기가 out_of_scope라고 판단해도 **KB에 근거가 있으면 KB로 답한다.**
4. 고객 화면에 `[PHONE]` 같은 내부 토큰이 나가지 않는다. 모델은 토큰을 "고객이 제공함"으로 이해하고
   "말씀하신 연락처" 식으로 표현한다. **PII는 계속 AI 제공자에게 나가지 않는다.**
5. (결정 필요) 고객이 예약·요청을 **확정**하면 사람에게 전달된다.

## 6. 제약

- **모더레이션(FR-069)**: 이력을 붙여도 출력 모더레이션은 그대로 필수 — 변경 없음.
- **PII 최소화(PRV Stage 5)**: 이력 턴도 **전부 `scrubPii()` 후** 전달. 원문 복원 금지.
  주문 컨텍스트(`orderContext`)의 기존 예외는 유지.
- **토큰 비용**: 턴당 입력이 늘어난다. 예산: 최근 12메시지 / 6,000자 상한
  (≈ 입력 +1.5~3k 토큰/턴). 코칭 채팅의 `HISTORY_TURNS=16 / 8,000자` 선례보다 작게 잡는다.
- **프로바이더 규칙**: Anthropic은 첫 메시지가 `user`여야 하고 같은 역할이 연속되면 안전하지 않다 →
  선행 assistant 턴 제거, 연속 동일 역할은 병합.
- **시스템 메시지**(동의 안내·핸드오프 공지·첨부 수신 등)는 모델 이력에서 제외한다. 모델이 따라 하면 안 되는
  정형 문구이기 때문이다. 상담원 발화는 assistant로 포함해 AI가 상담원 이후 대화를 이어갈 수 있게 한다.
- **스키마 변경 없음**(G1~G6). G7은 기존 핸드오프·이슈 체계 재사용 여부에 따라 결정.
- 콘솔 경로(`knowledge.service` KB 질의, `board-review` 시뮬레이션)는 단발 질의라 이력이 없다 → 변경 없음
  (새 인자는 선택형).
