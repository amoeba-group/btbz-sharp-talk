| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-20 |
| 요청 | ① `/admin`에 통계 추가 — **전체 테넌트별** ② `/statistics`를 **노출 > 접속 > 대화 > 에이전트 > 상담원 이관 > 평가 > 종료** 순으로 배열, 각 항목은 테넌트별 집계 |
| 유형 | 요구사항 (REQ→PLN→승인→구현) |
| 선행 | REQ/PLN-260920(노출·접속 통계) — 깔때기 앞 2칸이 이 작업으로 이미 존재 |

## 1. AS-IS

### 1.1 어드민 콘솔에는 통계가 없습니다

`/admin` 개요 화면의 KPI 4장 중 **3장이 비어 있습니다**:

```tsx
<KpiCard label={t('totalTenants')} value={totalTenants} />          // 유일한 실값
<KpiCard label={t('activeTenants')} value="—" hint={t('comingSoon')} />
<KpiCard label={t('aiEngines')}     value="—" hint={t('comingSoon')} />
<KpiCard label={t('conversations')} value="—" hint={t('comingSoon')} />
```

어드민 메뉴는 개요·테넌트·어드민 관리자·AI 엔진·감사 로그 5종이고 **통계 항목 자체가
없습니다.** 운영사는 "어느 테넌트가 실제로 쓰고 있는지"를 콘솔에서 볼 수 없습니다.

### 1.2 테넌트 통계는 시스템 관리자에게 **의도적으로 막혀** 있습니다

`analytics.controller.ts`의 게이트에 이유가 적혀 있습니다:

```ts
// …admin, and a null tenant here would aggregate every tenant into one table —
// a cross-tenant leak wearing a chart.
private tenantOf(user: Principal): number {
  const tenantId = tenantScope(user);
  if (tenantId == null) throw new BusinessException(ERROR_CODE.FORBIDDEN, …);
}
```

즉 **"전 테넌트를 한 덩어리로 합산하는 것"이 금지**된 것이지, 테넌트별로 나눠 보는 것이
금지된 게 아닙니다. 이번 요구("전체 **테넌트별**")는 바로 그 안전한 형태이므로, 기존
라우트를 여는 게 아니라 **어드민 전용 라우트를 따로** 두는 것이 맞습니다.

### 1.3 7단계 데이터 가용성 — 전부 기존 컬럼으로 도출 가능

| # | 단계 | 출처 | 상태 |
|---|---|---|---|
| 1 | 노출 | `sessions` 행 수 | ✅ (PLN-260920) |
| 2 | 접속 | `sessions.open_count`(+대화로 유도) | ✅ (PLN-260920) |
| 3 | 대화 | `conversations` | ✅ |
| 4 | 에이전트 | `messages.sender_type='ai'` 있는 대화 | ✅ (기존 `senderCountsByConversation` 재사용) |
| 5 | 상담원 이관 | `conversations.escalated` | ✅ |
| 6 | 평가 | `conversations.csat_rating IS NOT NULL` | ✅ |
| 7 | 종료 | `conversations.ended_at IS NOT NULL` | ✅ |

**신규 수집은 필요 없습니다.** 새 테이블·새 이벤트 없이 기존 데이터의 배열만 바뀝니다.

### 1.4 `/statistics` 현재 배열

```
질문 분석 · 노출·접속 · 채널 · 상담원 · 처리 · 만족도 · 시간대
```

탭 7개가 **성격별**로 놓여 있고 고객이 지나가는 **순서와 무관**합니다. 요청하신 배열은
같은 데이터를 **여정 순서**로 다시 세우는 것입니다.

## 2. TO-BE

### 2.1 어드민: 테넌트별 통계 화면 신설

`/admin/statistics` — 테넌트 한 행에 7단계 수치. 운영사가 한 화면에서
"어느 테넌트가 살아 있고, 어디서 막히는가"를 봅니다.

### 2.2 테넌트 콘솔: 7단 깔때기

`/statistics`에 **여정** 관점을 도입해 7단계를 한 줄로 보여주고, 기존 렌즈 탭들은
각 단계의 상세로 연결합니다.

## 3. 제약·리스크

### 3.1 단계는 부분집합이 아닙니다 — 깔때기로 그리면 거짓말이 됩니다

3~7단계는 **서로 부분집합이 아닙니다**:
- 상담원 이관된 대화도 평가를 받을 수 있고, 평가 없이 종료될 수도 있습니다.
- **종료**는 이관·평가와 **직교**합니다(이관된 대화도 결국 종료됨).

따라서 1→2→3까지는 진짜 깔때기(각 단계가 앞 단계의 부분집합)이지만, 4~7은
**"대화 중 몇 %가 이랬나"** 를 보는 **속성 분해**입니다. 화면이 이 둘을 같은 모양으로
그리면 "종료율 95%인데 평가율 3%라 뭔가 잘못됐다"는 오독을 부릅니다.
→ **1~3은 깔때기, 4~7은 대화 기준 비율**로 시각적으로 구분해야 합니다.

### 3.2 "에이전트" 단계의 뜻이 모호합니다 (O1)

요청의 4번 항목이 두 가지로 읽힙니다:
- (a) **AI 에이전트가 응답한 대화 수** — 깔때기 위치상 가장 자연스러움(대화 다음, 이관 앞)
- (b) 에이전트별 분해 축(현재 `/statistics`의 "상담원" 탭)

본 REQ는 **(a)** 로 가정했습니다. 순서가 `대화 > 에이전트 > 상담원 이관`이라
"AI가 받았다 → 사람에게 넘겼다"의 흐름으로 읽히기 때문입니다.

### 3.3 어드민 화면의 크로스테넌트 노출 범위

테넌트별 **집계 수치**만 노출하고 대화 내용·고객 정보는 일절 포함하지 않습니다.
`@AdminOnly()` + 감사 로그 대상 여부는 PLN에서 결정합니다.

### 3.4 비용

테넌트 수 × 7지표를 매 조회마다 계산하면 테넌트가 늘수록 느려집니다. 현재 스테이징
6개 수준이라 단순 집계로 충분하지만, **테넌트별 1쿼리 반복(N+1)은 금지**하고 단일
GROUP BY로 뽑아야 합니다.

### 3.5 소급 한계

**노출·접속은 2026-09-20부터 수집**됩니다(PLN-260920). 그 이전 구간은 1·2단계가 비고
3단계부터만 값이 있습니다 → 화면에 수집 시작일 명시 필요.
