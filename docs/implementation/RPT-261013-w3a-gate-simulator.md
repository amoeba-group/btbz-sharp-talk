### How it works (one paragraph)

The decision is three questions asked in the order chat already asked them. (1) **`decideGuestGate`**: an unverified visitor of a `login_guidance` agent is measured on the guest-visible scope *and* the audience (strict confidence: while the vector leg is down it stays 0.2, so an outage never loosens the gate); below `GUEST_GATE_CONFIDENCE` the visitor gets the sign-in prompt. (2) The audience-scoped answer: in chat this is `answer.confidence` (the model call's own retrieval, carrying the order / partner-data floors); the simulator measures the same thing with `groundingReport(…, queries)` so a degraded vector leg may still earn the capped keyword confidence exactly as `answer()` computes it. (3) **`decideLowConfidence`**, reached when the answer is under the 0.45 handoff bar: a signed-in partner below manager gets one extra grounding check with the manager audience → `role_manager_only`; else `embedder_degraded` when the vector leg was down (the 0.2 sentinel says nothing about the question), else `low_confidence`. `decideGate` composes the three for the simulator, the golden runner and the calibration; chat calls (1) and (3) at the points its flow already asks them, so every customer-visible outcome is what it was and the 312-combination parity spec proves chat and simulator agree. Every decision stores `retrieval_trace` extras (never the question): refusals and hand-offs on the system message, a **pass on the AI turn** (when a gate was actually asked). The console simulates a viewer with a synthetic identity run through the real `audienceOf`; the reply text comes from the very helpers the refusal branches use.

## 3. Design decisions and deviations from the brief / PLN

1. **`decideGate` signature**: `decideGate(rag, { tenantId, agentId, identity, query }, opts)` — the brief's `(tenantId, agentId, identity, query, history?)` with the RAG port made explicit (so a spec passes a double) and history folded into `query` by the caller (`retrievalQuery(history, text)`, as chat has always done).
2. **Not a Nest provider**: free functions over a small `GateRag` port — no module wiring, no constructor change in `ChatService`; positional specs that mock `groundingConfidence` only keep working because the decision falls back to the bare number when `groundingReport` is absent.
3. **Trace content**: matched categories are stored as **names** (operator content, top 3, ≤ 48 chars), not ids — no per-turn lookup; the top-3 document ids are stored too. Numbers are rounded to 4 decimals (a stored `grounded: 0.8599999999999999` is now `0.86`).
4. **A pass is recorded when a gate was asked** (a guest of a `login_guidance` agent), not on every AI turn: an open agent or a signed-in session never measured anything, and those turns stay byte-identical. Refusals and hand-offs (including every low-confidence hand-off, for every tenant) carry the measurement — the data is already in hand.
5. **Provider word in traces**: the gateway's own word (`voyage` / `stub`), `none` for no vector leg, and `degraded` when the leg should have run and did not — the convention SG-84 already uses on the AI turn.
6. **Simulator talks to the default agent** when none is picked; `guest` of an `open` agent is simply `allow` and the card says why (policy note).
7. **Golden**: `expect_gate: refuse` means ANY decision but `allow`; an expected refusal is not graded on the question's listed facts (they are not in the notice); an expectation needs a viewer (**E5145**; clearing the viewer clears it). A viewer question with a partner context still gets the partner block when the gate lets it through. Bulk TSV accepts the two as optional 5th/6th columns (an addition; documented in the bulk hint).
8. **Calibration scope**: only guest questions move with the bar; signed-in questions are carried as measured (they never meet it) and reported per audience at every bar. Positive class = refuse; leak = false-allow; recommendation = fewest leaks → best F1 → fewest over-refusals → **strictest** equal bar; none for a one-sided set; never a bar ≤ 0.2. Exit codes: **0** meaningful + leak-free bar, **1** could not run, **2** meaningful but no leak-free bar (or too few labels), **3** not meaningful (stub / keyword-only / degraded). On exit 3 the table is printed "for illustration only", the JSON has `report.recommendation: null`.
9. **Starter CSV**: 30 DRAFT rows (12 public how-to/login/registration asked as a guest → `allow`; 12 partner-only (cancellation policy, rates, promotions, bookings) asked as a guest → `refuse`; 6 manager-only (payout / bank account, settlement, staff permissions) asked as a receptionist → `refuse`), Vietnamese and English, derived from the Go2Joy KB categories; the header asks Go2Joy ops to review each row's tier and wording.
10. **Console**: the viewer select sits next to the agent picker (the action row wraps in the narrow column); a viewer change clears the previous result; the golden editor's expectation select is disabled until a viewer is chosen; the Q&A error toast is now sticky (error toasts are manual-close).

## 6. Migration (schema-changing change — `## Migration`)

- SQL: `sql/261019-golden-gate-columns.sql` — `ALTER TABLE golden_questions ADD COLUMN audience varchar(16) NULL, ADD COLUMN expect_gate varchar(8) NULL;` and `ALTER TABLE golden_run_items ADD COLUMN audience varchar(16), expect_gate varchar(8), gate_decision varchar(24), gate_confidence decimal(4,3), gate_threshold decimal(4,3), gate_top_similarity decimal(4,3), gate_vector_provider varchar(16)` (all NULL). Additive, nullable, no `AFTER`, no backfill (NULL = today's behaviour).
- **Order: apply the SQL to the target DB BEFORE deploying the code** (old code + new columns = safe; new code + old schema = 500 on the first golden read). Staging runs `DB_SYNCHRONIZE=false`, so it must be applied by hand there. Guard each statement with `SHOW COLUMNS FROM … LIKE …`.
- Per environment: [ ] dev `db_sharptalk` · [ ] staging · [ ] production (TBD).
- Rollback: the `DROP COLUMN` statements in the file's footer (roll the code back first — shipped code selects the columns).
- Behaviour after deploy: nothing changes for a tenant that does not use the new fields. Traces of refusals / hand-offs carry extra keys; a guest-gated pass records its trace.

## 8. Open follow-ups / risks
